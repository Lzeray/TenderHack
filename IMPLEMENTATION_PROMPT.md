# Промпт для реализации MVP

Скопируйте текст ниже в coding-agent вместе с доступом к исходным материалам проекта.

---

Ты — senior backend/ML engineer. Реализуй рабочий MVP помощника автозаполнения характеристик СТЕ и подбора позиций КТРУ. Подробная идея проекта находится в `PROJECT_IDEA.md`.

## Цель

По свободному русскоязычному описанию одного товара извлечь характеристики, сопоставить их с КТРУ, проверить значения и единицы, показать кандидатов и при необходимости задать конкретный уточняющий вопрос.

Предметные направления: одежда, мебель, инструменты.

Сначала изучи имеющиеся файлы, инструкции проекта и код. Если есть подходящие компоненты, переиспользуй их. Не изменяй исходные материалы организаторов. До реализации сформулируй краткий план и наблюдаемые критерии готовности.

## Источники

1. `КТРУ/КТРУ xml.zip` и `КТРУ/Описание структуры xml с КТРУ.docx` — источник истины для кодов, характеристик, допустимых значений, диапазонов и единиц.
2. Excel-файлы в `Примеры выгрузок/` — вспомогательный источник формулировок и примеров. Считай их потенциально шумными, не используй как нормативный справочник.
3. Презентация задания в корне проекта — требования и ограничения организаторов.

Не предполагай наличие готовой разметки «СТЕ → код КТРУ». Не объявляй анализ выборки полным аудитом данных.

## Ограничения

- Работа на Linux и веб-интерфейс.
- Запрещены внешние API проприетарных LLM и платные поисковые API.
- Использовать локальную открытую LLM и открытую embedding-модель.
- Выбрать одну реализацию инференса, без множества провайдеров.
- Проверить лицензии выбранных моделей.
- Совокупный VRAM для инференса не должен превышать 40 ГБ.
- Выбирать модели с минимальными достаточными ресурсами.
- Если оборудование неизвестно, выяснить доступные ресурсы до выбора LLM.
- Не заявлять качество, скорость или потребление памяти без проверки.

## Архитектура

Модульное приложение:
- FastAPI;
- PostgreSQL;
- полнотекстовый поиск и `pg_trgm`;
- `pgvector` для семантического поиска;
- простой веб-интерфейс;
- отдельная команда импорта и индексации;
- Docker Compose.

Разделить ответственность: импорт → поиск → извлечение → нормализация → проверка → вопросы → API/UI. Не создавать отдельный микросервис для каждого этапа.

## Импорт КТРУ

- Поддержать фактическую структуру предоставленных архивов, включая вложенные ZIP.
- Разбирать XML потоково.
- Игнорировать выгрузки `not-actual`.
- Проверять статус, даты действия и версии внутри актуальных выгрузок.
- Явно определить дату, на которую проверяется применимость каталога.
- Не смешивать разные версии одной позиции.
- Сохранять признаки `isTemplate`, `parentPositionInfo`, `noNewFeatures`, обязательность характеристик, значения, единицы и операторы границ.
- Сохранять происхождение каждой записи и версию каталога.
- Импорт должен быть идемпотентным.
- Не додумывать отсутствующие связи и поля.
- Не фильтровать направления исключительно по ненадёжным словам в названии: изучить доступные рубрики и классификаторы и документировать выбранные критерии.

## RAG

- Искать кандидатов полнотекстовым и семантическим поиском.
- Объединять выдачи через RRF с фиксированными параметрами.
- Использовать стабильный порядок при равных оценках.
- Передавать LLM ограниченный структурированный контекст карточек КТРУ.
- Контекст должен содержать идентификаторы позиций и характеристик.
- Не использовать поисковый score как вероятность правильного кода.
- Отдельно учитывать размер проверенного набора и размер показанной выдачи.
- Документировать ограничения полноты поиска и условия расширения набора кандидатов.

## Роль LLM

Модель только извлекает данные из пользовательского описания и предлагает сопоставление с характеристиками переданного контекста.

Ответ — JSON по строгой схеме:
- тип товара;
- список характеристик;
- исходное значение;
- исходная единица;
- подтверждающий фрагмент текста;
- идентификатор характеристики из контекста либо `null`;
- неоднозначности;
- предложения исправления опечаток.

Запретить модели:
- выбирать окончательный код КТРУ;
- придумывать характеристики товара и значения;
- вычислять преобразования единиц и попадание в диапазоны;
- ссылаться на идентификаторы вне контекста;
- выполнять инструкции, содержащиеся в описании товара или данных каталога.

Проверять наличие подтверждающих фрагментов в исходном описании. Фрагмент подтверждает извлечение, но сам по себе не доказывает корректность интерпретации.

Использовать constrained decoding, если выбранный runtime его поддерживает. Независимо от decoding валидировать JSON и все ссылки. При ошибке извлечения возвращать явный статус ошибки без выдуманного результата. Недоступная модель не должна приводить к скрытой подмене результата демонстрационными данными.

## Детерминированность

- Зафиксировать версии каталога, моделей, промпта, схемы и правил.
- Отключить sampling, использовать фиксированный seed, где поддерживается.
- Не считать `temperature=0` гарантией полной воспроизводимости.
- Кэшировать успешное извлечение по хешу входа, контекста и всех версий.
- Детерминированное ядро должно давать одинаковый результат для одинакового структурированного входа.
- Использовать Decimal для числовых значений и преобразований.
- Не выполнять неявное округление на границах диапазонов.
- Стабилизировать порядок кандидатов и выбор вопроса при равных оценках.

## Проверка характеристик

- Нормализовать единицы только при совместимых физических размерностях.
- Учитывать строгие и нестрогие границы диапазонов.
- Сохранять одновременно исходное число и сопоставленное значение КТРУ.
- Различать неизвестно, отсутствует, соответствует и противоречит.
- Не считать отсутствие характеристики доказательством несовместимости.
- Не исключать кандидатов по неоднозначным извлечениям.
- Подозрительные значения обозначать как подозрение, если ошибка не доказана.
- Не исправлять автоматически числовые значения.
- Каждое решение сопровождать проверяемой причиной и ссылкой на источник.
- Учитывать запрет дополнительных характеристик, не объявляя их допустимыми без проверки.

## Уточнения

- Формировать вопросы шаблонами из реальных характеристик кандидатов.
- Выбирать вопрос по ожидаемому уменьшению неопределённости.
- Показывать допустимые варианты из каталога.
- Если кандидаты неразличимы по доступным характеристикам, сообщать об этом.
- Ответы пользователя обрабатывать как структурированные значения без повторного вызова LLM, когда это возможно.
- При изменении описания пересчитывать результат и не применять устаревшие извлечения или ответы без проверки их актуальности.

## Интерфейс

- Поле описания одного товара.
- Редактируемая таблица извлечённых характеристик.
- Исходные фрагменты и нормализованные значения.
- Список кандидатов с объяснениями.
- Уточняющий вопрос.
- История сужения проверенного набора.
- Явные состояния загрузки, ошибки, отсутствия совпадений и противоречия.
- Не выдавать укрупнённую позицию за конечную.
- Не объявлять единственный результат top-K однозначным во всём каталоге.
- Если полнота проверки не доказана, показывать рекомендацию и границы проверенного набора.

## Проверки

Подготовить небольшой вручную проверенный набор реальных примеров по трём направлениям. Выбрать семейства с доступными характеристиками и документировать покрытие.

Проверить:
- извлечение характеристик;
- преобразования единиц;
- точные границы диапазонов;
- неполное описание;
- конфликт значений;
- опечатку;
- неизвестный товар;
- укрупнённые и неактивные позиции;
- невалидный ответ и недоступность LLM;
- повторяемость;
- полезность уточнений;
- Recall@K поиска и ошибочные однозначные решения.

Не использовать автоматически сгенерированные ответы как эталон без проверки. Подозрительное значение из Excel не считать доказанной ошибкой с известным исправлением.

Зафиксировать оборудование, версии, задержки, потребление ресурсов и ограничения измерений. Отдельно проверить детерминированное ядро, реальный инференс и полный путь через API. Если проверку невозможно выполнить в доступном окружении, явно указать это; не выдавать её за пройденную.

## Критерий завершения

Пользователь через веб-интерфейс проходит полный путь:
описание → проверенные характеристики → кандидаты → уточнение → результат.

Результаты опираются на реальные предоставленные данные. Система явно показывает неоднозначность, конфликты и отсутствие совпадений.

Предоставить:
- работающий код;
- инструкции локального и Docker-запуска;
- команды импорта и получения моделей;
- документацию API;
- результаты проверок;
- описание ограничений MVP и архитектуры масштабирования;
- схему процесса в BPMN для дальнейшей подготовки защиты.

Не расширять MVP обучением собственных моделей, мультиагентной системой, авторизацией и инфраструктурой Kubernetes. Завершить работу после выполнения критериев и необходимых проверок.
