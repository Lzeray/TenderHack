# Идея проекта: помощник заполнения СТЕ и подбора КТРУ

## Цель

Веб-приложение по свободному русскоязычному описанию одного товара извлекает характеристики, приводит их к стандарту КТРУ и помогает выбрать подходящую конечную позицию каталога. Если данных недостаточно или они противоречивы, приложение объясняет проблему и предлагает конкретный следующий шаг.

Предметные направления MVP: одежда, мебель, инструменты.

**Основной принцип: открытая LLM интерпретирует текст, КТРУ задаёт ограничения, программный код принимает проверяемое решение.**

## Требования задания

- Ввод описания на естественном языке, включая опечатки и неполные данные.
- Сопоставление названий характеристик, значений и единиц измерения.
- Проверка допустимых значений и диапазонов по КТРУ.
- Поэтапное сужение кандидатов и конкретные уточняющие вопросы.
- Объяснение обнаруженных ошибок и выполненных преобразований.
- Веб-интерфейс, работа на Linux, возможность масштабирования.
- Для защиты проекта — схема процесса в нотации BPMN.

Внешние API проприетарных LLM и платные поисковые API запрещены. Разрешены открытые модели при суммарном потреблении VRAM для инференса не более 40 ГБ; предпочтение отдаётся лёгким решениям.

## Исходные данные и наблюдения

### КТРУ — источник истины

Исходные материалы: `КТРУ/КТРУ xml.zip` и `КТРУ/Описание структуры xml с КТРУ.docx`.

В XML присутствуют коды и версии позиций, ОКПД2, статусы, даты применения, характеристики, обязательность, допустимые значения, диапазоны с операторами границ, единицы ОКЕИ, признак укрупнённой позиции и родительские связи.

В просмотренной выгрузке `all_actual` встретился статус `TERMINATED`. Поэтому имя файла не заменяет проверку статуса, дат и версии. Укрупнённую позицию нельзя выдавать за конечный код.

### Excel — источник формулировок и примеров

В `Примеры выгрузок/` находятся три файла примерно по 100 тысяч строк. Поля: ID СТЕ, название, модель, производитель, страна, характеристики через `|`.

В просмотренных примерах обнаружены подозрительные размеры и массы, повторяющиеся характеристики с разными значениями, нули, «не задано», смешение размеров изделия и упаковки. Это выборочные наблюдения, а не полный аудит.

Excel полезен для поиска синонимов и подготовки тестовых случаев, но не должен заменять нормативные ограничения КТРУ. В просмотренных столбцах нет явной разметки «СТЕ → код КТРУ».

## Выбранный подход: RAG + детерминированная проверка

```text
Подготовка данных:
XML КТРУ → нормализованная база → полнотекстовый и векторный индексы

Обработка запроса:
Описание товара
    ↓
Гибридный поиск кандидатов КТРУ
    ↓
Описание + схемы найденных позиций → локальная открытая LLM
    ↓
Структурированные характеристики с подтверждающими фрагментами текста
    ↓
Нормализация и проверка программными алгоритмами
    ↓
Совместимые кандидаты / уточняющий вопрос / конфликт / отсутствие совпадений
```

### 1. Подготовка каталога

- Потоковый импорт XML, включая вложенные ZIP.
- Исключение выгрузок `not-actual` и проверка статусов, дат, версий.
- Сохранение характеристик, значений, единиц и точных границ диапазонов.
- Сохранение происхождения записей и версии каталога.
- Идемпотентный импорт и индексация до обработки пользовательских запросов.

### 2. Retrieval

Гибридный поиск объединяет полнотекстовое/нечёткое совпадение и семантический поиск. Результаты объединяются через RRF с фиксированными параметрами и стабильным порядком при равных оценках.

В контекст модели передаются ограниченные структурированные карточки КТРУ с идентификаторами позиций и характеристик. Поисковый рейтинг определяет порядок кандидатов, но не является вероятностью правильности кода.

Кандидаты embedding-моделей для сравнения: `intfloat/multilingual-e5-small` и `BAAI/bge-m3`. Выбор — по качеству и ресурсам на наших примерах; измерений пока нет.

### 3. Роль открытой LLM

Модель извлекает только явно указанные свойства и предлагает сопоставление с характеристиками переданного контекста. Ответ — JSON по строгой схеме:

- тип товара;
- характеристики и исходные значения;
- исходные единицы;
- подтверждающие фрагменты описания;
- идентификаторы характеристик каталога либо `null`;
- неоднозначности и предложения исправления опечаток.

Модель не выбирает окончательный код, не придумывает отсутствующие свойства, не преобразует единицы и не проверяет диапазоны.

### 4. Детерминированное ядро

Программный код валидирует JSON и ссылки, преобразует совместимые единицы, сопоставляет справочные значения, проверяет диапазоны и вычисляет совместимость кандидатов.

Для чисел используется точная десятичная арифметика. Например, из извлечённых `500 г` алгоритм получает `0,5 кг`; исходное число сохраняется отдельно от сопоставленного значения или диапазона КТРУ.

Статусы характеристики: соответствует, противоречит, требует уточнения, отсутствует, не сопоставлена. Неизвестное значение не считается нулём. Отсутствие характеристики у позиции не всегда означает несовместимость. Неоднозначное извлечение не служит основанием для жёсткого исключения кандидата.

## Воспроизводимость

- Фиксируются версии каталога, моделей, промптов, схем и правил.
- Фиксируются параметры поиска и правила разрешения равных оценок.
- Sampling отключается; seed фиксируется там, где поддерживается.
- Успешное извлечение кэшируется по хешу входа, контекста и всех версий.
- Финальные проверки воспроизводимы для одинаковых структурированных данных.
- Невалидный ответ LLM возвращает явную ошибку извлечения.

`temperature=0` и фиксированный seed не гарантируют одинаковый ответ модели на любом оборудовании. Кэш обеспечивает повторное использование результата для идентичного запроса в рамках неизменных версий, а не абсолютную воспроизводимость нового инференса.

## Уточняющие вопросы

Вопросы формируются шаблонами из реальных характеристик оставшихся кандидатов. Выбирается характеристика, ответ на которую лучше всего уменьшит неопределённость; варианты берутся из КТРУ.

Если доступные характеристики не различают позиции, система сообщает об этом и предлагает уточнить тип или назначение товара. Не каждое дополнительное свойство обязательно меняет набор кодов.

Ответ через структурированный элемент интерфейса обрабатывается без повторного обращения к LLM, когда это возможно.

## Пользовательский интерфейс

- Поле описания одного товара.
- Редактируемая таблица извлечённых характеристик.
- Исходные фрагменты, нормализованные значения и объяснения преобразований.
- Кандидаты КТРУ с причинами соответствия и конфликтами.
- Следующий уточняющий вопрос.
- История изменения проверенного набора кандидатов.
- Явные состояния загрузки, ошибки и отсутствия совпадений.

Итоговые статусы: предложена конечная позиция, нужно уточнение, обнаружено противоречие, ничего подходящего не найдено.

Единственный кандидат в top-K не доказывает однозначность во всём каталоге. Нужно различать размер проверенного набора, количество совместимых позиций и число показанных результатов. Если полнота поиска не подтверждена, результат называется рекомендацией с указанием границ проверки.

## Границы MVP

Один законченный сценарий: описание → проверенные характеристики → кандидаты → уточнение → результат.

Подготовка каталога охватывает три направления. Качество первой версии подтверждается на выбранных семействах товаров с доступными характеристиками и вручную проверенными примерами. Не предполагается, что каждый товар обязательно имеет соответствующую конечную позицию КТРУ.

За рамками первой версии: несколько товаров в запросе, обучение собственных моделей, мультиагентность, авторизация, Kubernetes и обработка всех исключительных случаев.

## Техническая основа и масштабирование

- FastAPI — API и бизнес-логика.
- PostgreSQL — каталог, характеристики, версии, происхождение данных.
- Полнотекстовый поиск и `pg_trgm` — поиск по словам и опечаткам.
- `pgvector` — семантический поиск.
- Локальная открытая LLM — извлечение.
- Веб-клиент и Docker Compose.
- Отдельная команда импорта и индексации.

Начальная архитектура — модульное приложение. Импорт и индексация выполняются заранее; проверки работают по ограниченному набору кандидатов. API не хранит единственную копию пользовательского состояния в своей памяти. При росте нагрузки инференс и API можно масштабировать независимо.

Масштабируемость подтверждается измерениями задержки, памяти и пропускной способности, а не только выбором стека.

## Проверка качества

Нужен небольшой вручную проверенный набор по трём направлениям, включая неполные описания, опечатки, противоречия, границы диапазонов и неизвестные товары.

Измерять:
- Recall@K поиска;
- корректность извлечения и сопоставления характеристик;
- преобразование единиц и обработку границ;
- частоту ошибочных однозначных решений;
- полезность уточняющих вопросов;
- повторяемость результатов;
- задержку, включая p95, и потребление ресурсов.

Подозрительные значения из Excel не считать готовым эталоном исправления без проверки.

## Рассмотренные альтернативы

| Подход | Преимущество | Ограничение |
| --- | --- | --- |
| Полнотекстовый поиск + правила | Быстрый и объяснимый baseline | Слабее на непрямых формулировках |
| Только векторный поиск | Семантические совпадения | Не гарантирует соответствия числам и ограничениям |
| Только LLM с контекстом | Гибкое понимание текста | Непроверяемые догадки и вариативность |
| Классификатор кодов | Быстрый инференс после обучения | Нужна разметка, сложнее обновлять каталог |
| Гибридный RAG + проверка | Смысловой поиск и проверяемое решение | Требует качественного импорта и нормализации |
