# Подбор КТРУ по описанию товара (TenderHack, MVP)

**Текущий пользовательский режим — живой двухветочный поиск:** [docs/LIVE_SEARCH.md](docs/LIVE_SEARCH.md).
При вводе автоматически извлекаются предмет/свойства, показываются все подходящие позиции КТРУ и
отдельно примеры товаров из XLSX. Qwen предлагает дополнительный разбор после паузы; новые
модельные условия применяются только после подтверждения. Предварительный выбор типа не обязателен.
Запуск: `RECOGNITION_MODE=hybrid SEMANTIC=1 LLM_MODE=always`.

## React-интерфейс «ТендерМаркет»

Текущий frontend — React 19 + Vite 8 в `frontend/`. Старые HTML/CSS/JS из `ktru_assist/web/`
удалены. FastAPI отдаёт готовую сборку `frontend/dist/` на `/`, ресурсы — на `/static/assets/`.

- Карточки товаров с краткими характеристиками, производителем и подробным просмотром.
- Автодополнение по реальным наименованиям КТРУ, выбор мышью и клавиатурой.
- Заметные противоречия, исправление опечаток, предупреждения и состояния загрузки.
- Параметры товара, ручное редактирование, уточняющие вопросы и история сужения КТРУ.
- Раздельные вкладки СТЕ и КТРУ с собственными счётчиками; пагинация товаров.
- Адаптивный интерфейс: на телефоне параметры и уточнения сворачиваются.
- Иллюстрации показывают категорию, это не фотографии конкретных SKU. Цены и предложения
  поставщиков не выдумываются: карточки используют имеющиеся выгрузки.

Перед обычным запуском API один раз собрать frontend (из `frontend/`, Node 22.12+):

```bash
npm ci
npm run build
```

Для разработки интерфейса: `npm run dev` из `frontend/`, затем открыть `http://127.0.0.1:5173`.
Vite проксирует `/api` на уже запущенный backend `http://127.0.0.1:8000`.
После изменения исходников для обычного порта 8000 снова выполнить `npm run build`.
Dockerfile собирает React отдельным Node-этапом автоматически.

Проверки: `npm test` в `frontend/`, `pytest` из корня и
`node tools/ui_react_check.mjs http://127.0.0.1:8001 --screenshots` при запущенном Chrome/CDP
на порту 9333 и тестовом hybrid-сервисе. Скриншоты — `reports/react_desktop.png` и `reports/react_mobile.png`.
Старые браузерные скрипты для vanilla-интерфейса являются историческими; актуальный — `ui_react_check.mjs`.

## Быстрый старт (локально, Python 3.12)

```bash
pip install -r requirements.txt
# 1. Импорт: каталог с вложенными zip выгрузки nsiKTRUNew (not-actual пропускаются автоматически)
python -m ktru_assist.cli import --src "../КТРУ/КТРУ xml.zip" --db data/ktru.sqlite --as-of 2026-10-09
# 2. Актуальный живой путь без моделей (работает сразу после импорта)
RECOGNITION_MODE=hybrid SEMANTIC=0 LLM_MODE=off python -m ktru_assist.cli serve --port 8000
# С локальной Qwen в Ollama: заменить LLM_MODE=off на LLM_MODE=always.
# SEMANTIC=1 включается после подготовки ML-зависимостей и локального индекса (docs/SEMANTIC_PIPELINE.md).
# 3. Тесты и оценка
python -m pytest -q
python -m eval.run_eval --repeat 20                                  # кейсы разработки
python -m eval.run_eval --cases eval/holdout.jsonl --out reports/holdout_results.json
```

`--src` принимает каталог, отдельный zip (в том числе с вложенными zip) или XML.
Если исходный архив ещё не распакован, можно передать `"КТРУ/КТРУ xml.zip"` напрямую.
Путь зависит от расположения материалов; приведённый пример соответствует архиву рядом с клоном.
Для товаров СТЕ дополнительно выполнить импорт XLSX из `docs/STE_DATA.md` и построить индекс из
`docs/LIVE_SEARCH.md`. Без этих баз работает нормативный подбор КТРУ.

## Docker Compose (с OpenSearch)

Это исторический `rules`-вариант. Для текущего `hybrid` после импорта SQLite:

```bash
docker compose --profile live up -d ollama
docker compose --profile live exec ollama ollama pull qwen3:4b-instruct-2507-q4_K_M
docker compose --profile live up -d hybrid-app
```

Этот профиль не запускает OpenSearch. Ollama по умолчанию работает без резервирования GPU;
для целевого Linux-сервера доступ к NVIDIA нужно настроить отдельно. Контейнерный запуск
ещё не проверен; приведённые модельные задержки измерены локально, не в Docker.

```bash
docker compose --profile setup run --rm importer      # XML → data/ktru.sqlite
docker compose up -d opensearch
docker compose --profile setup run --rm indexer       # SQLite → индекс OpenSearch
docker compose up -d app                              # http://localhost:8000
```

> **Не проверено:** на машине разработки не было Docker, поэтому compose-файл и OpenSearch-бэкенд
> не запускались. Все замеры ниже сделаны со встроенным бэкендом `local-bm25`
> (`SEARCH_BACKEND=local`, по умолчанию). Бэкенд указывается в каждом ответе API.

Переменные окружения: `KTRU_DB`, `SEARCH_BACKEND` (`local` | `opensearch`), `OPENSEARCH_URL`,
`OPENSEARCH_INDEX`, `TOP_K` (50), `TYPE_FETCH_LIMIT` (1000).

## Архитектура

| Модуль | Файл | Ответственность |
| --- | --- | --- |
| Импорт каталога | `catalog/importer.py` | потоковый разбор XML, вложенные zip, выбор версии → статус → сроки, SQLite |
| Доступ к каталогу | `catalog/repository.py` | SQLite только на чтение, интервалы и допустимые значения |
| Нормализация | `nlp/normalize.py` | регистр, пробелы, «75см», «120х60», словоформы; история шагов |
| Опечатки | `nlp/typos.py` | словарь каталога, SymSpell + Дамерау–Левенштейн, только однозначные |
| Извлечение | `nlp/extract.py` | «свойство: значение», числа с единицами и сравнениями, логические и качественные значения, отрицания |
| Единицы | `units.py` | ОКЕИ → размерность, точный перевод внутри размерности |
| Поиск | `search/*` | OpenSearch или BM25: кандидаты по названию, словоформам и алиасам |
| Валидация | `validate.py` | valid / invalid / unknown для каждого свойства каждого кандидата |
| Ранжирование | `rank.py` | фиксированный ключ сортировки, компоненты в ответе |
| Уточнения | `clarify.py` | вопрос с минимальным худшим остатком кандидатов |
| Конвейер | `engine.py` | этапы сужения, решение о статусе |
| API/UI | `api.py`, `frontend/` | FastAPI и React/Vite |

Схема процесса в нотации BPMN 2.0: `docs/process.bpmn` (открывается в bpmn.io или Camunda Modeler).
Решения по данным: `docs/DATA.md`.

### Ключевые правила

- **Область проверки.** Поиск (top-K) используется только для того, чтобы определить тип товара — главное слово наименования.
  Затем из индекса берутся **все** активные позиции этого типа. Совпадение проверяется в этой полной области;
  если она обрезана лимитом, `matched` не выдаётся.
- **Тип по наименованию.** Если все слова наименования позиции есть в описании, область сужается до этого
  наименования. Это отдельный этап сужения, он виден в ответе.
- **Привязка значения к свойству** — только однозначная: по названию свойства рядом со значением, по единственному
  свойству нужной размерности или по значению из справочника. Иначе признак помечается `ambiguous`
  и предлагаются варианты.
- **Единицы.** 75 см = 750 мм, 0,5 кВт = 500 Вт. Вольты с ваттами не сравниваются: в этом случае проверка
  возвращает `invalid` с пояснением «несовместимая размерность».
- **Границы диапазонов** сохраняются из XML (`greater` / `greaterOrEqual`, `less` / `lessOrEqual`) и учитываются
  точно; смежные диапазоны объединяются только при общей точке.
- **unknown ≠ valid.** Отсутствие свойства у позиции даёт `unknown`; учитывается признак `noNewFeatures`.
- **`matched`** выдаётся, только если:
  - ровно одна активная конечная позиция (не шаблон);
  - тип подтверждён;
  - область проверена полностью;
  - нет неоднозначностей;
  - все обязательные свойства этой позиции подтверждены.
- **Ранжирование** не является вероятностью. Ключ сортировки: уровень совпадения наименования → доля слов
  наименования → покрытие терминов запроса → число проверенных условий → число непроверенных → код КТРУ.
- **Уточнения.** Для каждого незаданного свойства (и для «типа») считается, сколько кандидатов останется
  при каждом варианте ответа; пересекающиеся значения учитываются. Выбирается вопрос с минимальным
  худшим случаем. При равенстве первым идёт тип, затем обязательное свойство, затем код свойства.
  Если ни один вопрос не сокращает набор, предлагается ручной выбор.
- **Ручная правка** (`overrides`) приоритетнее текста: извлечённое значение помечается `overridden`.
- **Ответы на уточнения** привязаны к хешу текста: после изменения описания они не применяются
  (предупреждение `stale_answers`).

## API

- `POST /api/search` — `{text, overrides[], answers[], answers_query_hash, corrections{}, top_k}`.
  В ответе: `status` (`matched` | `clarification_needed` | `conflict` | `not_found` | `manual_choice`),
  `message`, `corrections`, `features`, `unrecognized`, `candidates` (с `checks` и `rank_components`),
  `stages`, `question`, `final_code`, `issues`, `completeness`, `versions`, `elapsed_ms`.
- `GET /api/catalog` — версия снимка, дата применимости, покрытие категорий, счётчики импорта.
- `GET /api/positions/{code}` — позиция со всеми характеристиками.
- `GET /health`.
- Интерактивная документация: `/docs` (FastAPI).

## Известные ограничения MVP

- Тип товара определяется по главному слову наименования КТРУ. Синонимы типа — только из
  `data/aliases.json` (например, «болгарка» не распознаётся).
- Габариты «120x60x75 см» без названий измерений не привязываются: признак `ambiguous`, свойство
  выбирает пользователь.
- Не все словоформы значений распознаются: «сетевой» ≠ «От сети», «раскладной» ≠ «Наличие механизма
  раскладывания». В таких случаях система задаёт вопрос, а не угадывает.
- Один товар на запрос. Подбор коммерческих СТЕ не реализован.

Последние пункты этого исторического раздела заменены текущими инструкциями: XLSX уже импортированы,
поиск примеров СТЕ реализован, Chrome-проверки проводятся. Независимой разметки поставщиков, замера
пикового CUDA VRAM и подтверждённого Docker/Linux-прогона пока нет. Текущий сервис рассчитан на один
API worker: ревизии сессий в памяти и сериализация ядра/LLM ограничивают многопользовательскую нагрузку.
Для нескольких workers нужен общий реестр ревизий и отдельная ограниченная очередь инференса;
наличие FastAPI/SQLite само по себе масштабируемость не доказывает.
