# Подбор КТРУ по описанию товара (TenderHack)

**Текущий пользовательский режим — живой двухветочный поиск:** [docs/LIVE_SEARCH.md](docs/LIVE_SEARCH.md).
При вводе автоматически извлекаются предмет/свойства и показываются подходящие позиции КТРУ.
Qwen дополняет результат после паузы; обязательного предварительного выбора типа нет.
Запуск: `RECOGNITION_MODE=hybrid SEMANTIC=1 LLM_MODE=always`.

**Подбор только по КТРУ (с 10.10.2026):**
- по типу находятся **все** позиции КТРУ: «стол» — все столы (кроме секций), «брюки» — и «Брюки спортивные»;
  какое наименование нужно, уточняется вопросом (`docs/KTRU_SEARCH_PLAN.md`);
- характеристика из описания, которая есть в КТРУ, — условие отбора: исключаются только позиции, где это
  свойство есть и значение ему противоречит (подходит одно из допустимых значений). Позиции без свойства
  остаются. Роль характеристики: основная — обязательна хотя бы в одной позиции типа, иначе неосновная
  (`role` в признаке);
- характеристика, которой нет в КТРУ, — дополнительная (на код не влияет). Сначала проверяется её смысл:
  оценки вроде «красивое» не принимаются. Затем — есть ли она у товаров этого типа в выгрузках СТЕ.
  Принятые запоминаются в памяти сессии, компактно (`ktru_assist/extras.py`, базы не меняются);
- названия и значения приводятся к написанию КТРУ («угловой», «угловая» → «Угловой»; `ktru_assist/canon.py`);
- внизу интерфейса — таблица обязательных характеристик оставшихся позиций: сначала общие для всех,
  заполненные можно исправить. Необязательные распознанные характеристики — отдельным блоком;
- уточняющие вопросы сначала о характеристиках, общих для всех оставшихся позиций;
- обязательные характеристики запрашиваются до конца: код выдаётся, когда позиция одна и её обязательные
  характеристики заполнены. Товары СТЕ не выдаются
  (`/api/products` выключен, включается `STE_PRODUCTS=on`).
- поиск идёт по скрытой строке «тип; ключ: значение»; в поле ввода по Enter исправляется только орфография.
  Ответы на вопросы, выбор варианта и правки сохраняются, пока их фрагмент есть в тексте
  (`ktru_assist/canonical.py`, `docs/PARSE_INPUT_PLAN.md`);
- Интерфейс после изменения JSX нужно собрать: `cd frontend && npm ci && npm run build`
  (сборка пишется в `ktru_assist/web`).

Веб-приложение: русскоязычное описание одного товара → нормализованные характеристики →
совместимые позиции КТРУ → уточняющие вопросы → конечный код.
Направления: одежда, мебель, инструменты.

**Ядро детерминированное:** словарная лемматизация (pymorphy3), поиск OpenSearch или встроенный BM25,
проверки — правила на `Decimal`. Каждое решение сопровождается причиной. Код выдаёт только ядро.

Режим `rules` — детерминированная базовая линия: словарный разбор, OpenSearch или BM25, проверки на `Decimal`.
Добавлен экспериментальный `RECOGNITION_MODE=semantic`: поиск rubert-tiny2 при наборе, локальная Qwen после Enter,
подтверждение интерпретаций и то же ядро. В нём алиасы, SymSpell и главное слово не обязательны.
**Запуск, актуальные измерения и ограничения:** [docs/SEMANTIC_PIPELINE.md](docs/SEMANTIC_PIPELINE.md).
**Подготовка XLSX:** [docs/STE_DATA.md](docs/STE_DATA.md), отдельная база `data/ste.sqlite`.

**Модели — необязательные и только локальные** (план улучшений `docs/PLAN.md`, выключены по умолчанию):
- **A-semantic** (`SEMANTIC=1`): энкодер `cointegrated/rubert-tiny2` (MIT) на numpy предлагает типы и значения
  для слов, которые правила не разобрали;
- **B** (`LLM_MODE=escalate`): по Enter и только по эскалации — один вызов `Qwen3-4B-Instruct-2507`
  (Apache 2.0, Q4_K_M) через локальный Ollama с JSON-схемой и контекстом из снимка КТРУ.

Выход моделей — гипотезы: они не меняют числа, единицы и отрицания из текста и не дают `matched`
без подтверждения пользователем. Контракты и правила завершения — `docs/CONTRACTS.md`, аудит — `docs/AUDIT.md`.

## Быстрый старт (Linux, Python 3.12)

**Данные.** В `main` базы КТРУ нет: её собирает импорт ниже из исходных XML организаторов. Сжатая готовая база
(`data/ktru.sqlite.gz`) и индекс портала лежат только в ветке `Lenaz`; если положить их в `data/`, при первом
запуске они распакуются сами, и импорт не нужен.

```bash
pip install -r requirements.txt
# 1. Импорт: каталог с вложенными zip выгрузки nsiKTRUNew (not-actual пропускаются автоматически)
python -m ktru_assist.cli import --src "КТРУ/КТРУ xml/КТРУ" --db data/ktru.sqlite --as-of 2026-10-09
# 2. Запуск API + веб-интерфейса (только ядро)
python -m ktru_assist.cli serve --port 8000        # http://127.0.0.1:8000
# 3. Тесты и оценка
python -m pytest -q
python -m eval.run_eval --repeat 20                                  # кейсы разработки
python -m eval.run_eval --cases eval/holdout.jsonl --out reports/holdout_results.json
```

С моделями (нужен установленный [Ollama](https://ollama.com) на этой же машине):

```bash
pip install -r requirements-ml.txt
tools/fetch_models.sh                              # rubert-tiny2 (sha256 проверяется) + ollama pull
SEMANTIC=1 LLM_MODE=escalate python -m ktru_assist.cli serve --port 8000
# сравнение конфигураций на одном наборе
python -m eval.run_benchmark --cases eval/cases.jsonl eval/holdout.jsonl \
    --configs core core_b_always core_sem_b core_b_nodraft --out reports/benchmark.json
```

`--src` принимает каталог, отдельный zip (в том числе с вложенными zip) или XML.
Если исходный архив ещё не распакован, можно передать `"КТРУ/КТРУ xml.zip"` напрямую.

### Ключевые правила

- **Область проверки.** Поиск (top-K) используется только для того, чтобы определить тип товара — главное слово наименования.
  Затем из индекса берутся **все** активные позиции этого типа. Совпадение проверяется в этой полной области;
  если она обрезана лимитом, `matched` не выдаётся.
- **Тип по наименованию.** Если все слова наименования позиции есть в описании, область сужается до этого
  наименования. Это отдельный этап сужения, он виден в ответе.
- **Привязка значения к свойству** — только однозначная: по названию свойства рядом со значением, по единственному
  свойству нужной размерности или по значению из справочника. Иначе признак помечается `ambiguous`
  и предлагаются варианты.
- **Единицы.** 75 см = 750 мм, 0,5 кВт = 500 Вт. Вольты с ваттами не сравниваются: в этом случае проверка
  возвращает `invalid` с пояснением «несовместимая размерность».
- **Границы диапазонов** сохраняются из XML (`greater` / `greaterOrEqual`, `less` / `lessOrEqual`) и учитываются
  точно; смежные диапазоны объединяются только при общей точке.
- **unknown ≠ valid.** Отсутствие свойства у позиции даёт `unknown`; учитывается признак `noNewFeatures`.
- **`matched`** выдаётся, только если:
  - ровно одна активная конечная позиция (не шаблон);
  - тип подтверждён;
  - область проверена полностью;
  - нет неоднозначностей;
  - все обязательные свойства этой позиции подтверждены.
- **Ранжирование** не является вероятностью. Ключ сортировки: уровень совпадения наименования → доля слов
  наименования → покрытие терминов запроса → число проверенных условий → число непроверенных → код КТРУ.
- **Уточнения.** Для каждого незаданного свойства (и для «типа») считается, сколько кандидатов останется
  при каждом варианте ответа; пересекающиеся значения учитываются. Выбирается вопрос с минимальным
  худшим случаем. При равенстве первым идёт тип, затем обязательное свойство, затем код свойства.
  Если ни один вопрос не сокращает набор, предлагается ручной выбор.
- **Ручная правка** (`overrides`) приоритетнее текста: извлечённое значение помечается `overridden`.
- **Ответы на уточнения** привязаны к хешу текста: после изменения описания они не применяются
  (предупреждение `stale_answers`), интерфейс показывает сброс.
- **Алиасы значений** (`data/value_aliases.json`): «сетевой» → «Тип питания = От сети» — только если такое свойство
  и значение есть у позиций области.
- **Части товара:** «чёрный каркас, красное сиденье» привязываются к «Цвет каркаса» и «Цвет сиденья» отдельно;
  цвет каркаса не переносится на сиденье, свойство без части — только по выбору пользователя.
- **Факт, требование, предпочтение:** «не менее 600 Вт» — требование (выполнимо, если какое-то допустимое
  значение КТРУ целиком ему удовлетворяет); «желательно …» — не жёсткое условие.
- **Правдоподобие:** «45 м» для высоты сиденья — предупреждение и подтверждение, не исправление на см и не запрет КТРУ.
- **Модели** дают только гипотезы со статусом «предложено»: `matched` с ними невозможен без подтверждения.
- **Версии запросов:** клиент применяет ответ только своей revision; поздний черновик не перезаписывает
  полный разбор той же версии; сервер помечает устаревшие ответы `stale` и не вызывает LLM для устаревшей версии.

## API

- `POST /api/search` — `{text, session_id, revision, stage, overrides[], answers[], answers_query_hash,
  corrections{}, rejected[], confirmed[], top_k}`.
  В ответе: `status` (`matched` | `clarification_needed` | `conflict` | `not_found` | `manual_choice`),
  `message`, `corrections`, `features`, `unrecognized`, `candidates` (с `checks` и `rank_components`),
  `stages`, `question`, `final_code`, `issues`, `completeness`, `versions`, `elapsed_ms`, а также
  `assertions`, `proposals`, `code_resolution`, `characteristics_completion`, `scope`, `providers`, `changes`,
  `timings`, `stale`, `preliminary`, `effective_at` — см. `docs/CONTRACTS.md`.
- `GET /api/providers` — состояние моделей и закреплённые ревизии.
- `GET /api/catalog` — версия снимка, дата применимости, покрытие категорий, счётчики импорта.
- `GET /api/positions/{code}` — позиция со всеми характеристиками.
- `GET /health`.
- Интерактивная документация: `/docs` (FastAPI).

## Эксперименты: словари и проблемы данных (10.10.2026)

Подробно — `docs/EXPERIMENTS.md`, воспроизведение — `experiments/`. Кратко:

- **Зависимость от словарей.**
  - Ручные словари (алиасы, части, правдоподобие) влияют на ±1–2 кода.
  - Словарь морфологии заменим бесловарным стеммером без потери качества (`KTRU_MORPH=snowball`).
  - Главная зависимость — от формулировок КТРУ. На реальных наименованиях поставщиков тип не находится у 40 %
    одежды и инструментов: большая часть — законные отказы (обувь, сумки, нет типа в снимке),
    остальное — синонимы.
- **Исправлено**:
  - небезопасные коды по словам наименования;
  - ложные части товара;
  - составные слова типа («дрель-шуруповерт», «лобзик электрический»);
  - чужой тип из слова после предлога;
  - тип из единственного наименования без подтверждения (на реальных СТЕ давал неверные коды);
  - противоречивые значения одного свойства (переизбыток данных);
  - привязка чисел;
  - обозначение размеров одежды.
- **Официальный бенчмарк** (`reports/bench/core_after_experiments.md`):
  - pass 1,0 на всех четырёх наборах;
  - 0 неверных автокодов;
  - автокоды там, где код запрещён, на синтетике: 6 → 0;
  - дошли до кода в диалоге: 0,938 → 0,982;
  - новый стресс-набор (917 кейсов): pass 1,0, неверных автокодов 0 (было 3 на 850).

## Результаты проверок после плана улучшений (10.10.2026)

Сервер: Linux, RTX 3070 Ti 8 ГБ, Python 3.12.3. **Реальный снимок КТРУ на сервер ещё не перенесён**, поэтому
всё ниже — на синтетическом каталоге-fixture или на моделях без каталога. Это проверка работоспособности,
а не оценка точности.

- **pytest:** 92 теста проходят, 4 smoke-теста на реальной базе пропущены (базы нет). Fixture-тесты покрывают
  п. 10.1–10.2 плана: координаты, «0,75 кВт = 750 Вт», «не менее» = ≥, отрицательные числа, части товара,
  алиасы значений, «45 м», гипотезы моделей, отказ и расхождение, версии и гонки, сбои провайдера, кэш.
  JS-правила применения ответов проверяются в node (`tests/web/`).
- **Интерфейс в браузере** (headless Chrome, `tools/ui_check.mjs`, fixture): 11/11 проверок —
  черновик, Enter, последняя версия при быстром вводе, части товара, подтверждение «45 м», сброс ответов,
  раздельные «код / заполнение». Задержка черновика «ввод → отрисовка» — 131–136 мс при debounce 120 мс
  (единичные замеры, fixture, локальная машина).
- **Энкодер:** numpy-реализация rubert-tiny2 совпадает с sentence-transformers (9 строк, max |Δ| = 1,2·10⁻⁷,
  `reports/encoder_check.json`). Кодирование 4 коротких строк на CPU — около 5 мс.
- **LLM** `qwen3:4b-instruct-2507-q4_K_M` (digest `0edcdef34593…`) через Ollama 0.34: занято 4,0 ГБ VRAM
  (весь GPU, включая модель); на fixture-бенчмарке задержка ответа p50 ≈ 1,25–1,3 с, p95 ≈ 2,0–2,5 с
  (n = 11–21), холодный старт около 10 с. На fixture все четыре конфигурации дают 0 ошибочных и
  0 небезопасных `matched` (28 синтетических кейсов) — каталог слишком мал, чтобы сравнивать качество.

**Что ещё нужно сделать на реальном каталоге:** импорт, `pytest` (smoke и проверка алиасов значений),

## Что не проверено

- **Всё на реальном каталоге после изменений S0–S8** (см. выше): качество моделей на реальных описаниях,
  выигрыш A-semantic и B, задержки на реальной области, алиасы значений против реального снимка.
- **OpenSearch-бэкенд и Docker Compose** — Docker не было на машине разработки; образ не включает модели.
- **Веб-интерфейс:** браузерная проверка — только на fixture и только Chrome.
- **Excel-выгрузки СТЕ** использованы только для изучения структуры. Алиасы составлены вручную и
  проверены по каталогу: тест `test_aliases_point_to_existing_heads`.

## Известные ограничения

- Тип товара определяется по главному слову наименования КТРУ и проверенным алиасам; новые синонимы
  типа («болгарка») распознаются только как предложения моделей с подтверждением.
- Габариты «120x60x75 см» без названий измерений не привязываются: признак `ambiguous`, свойство
  выбирает пользователь.
- Алиасы значений и границы правдоподобия составлены разработчиком: их должна подтвердить команда
  (`status=unconfirmed` в `data/plausibility_rules.json`).
- Модели не дают автоматического кода: при эскалации пользователь подтверждает трактовку одним нажатием.
  Задержка B (1–2,5 с на fixture) не ограничена числовым пределом; при таймауте остаётся ручной путь.
- Один товар на запрос. Подбор коммерческих СТЕ не реализован.

При `EXTRAS_LLM=on` (по умолчанию выключено; в `docker-compose.yml` включено) по Enter или после секунды без ввода

КТРУ/СТЕ. Модель должна быть установлена на сервере заранее; приложение её
не скачивает. [Настройка и ограничения](docs/QWEN_EXTRAS.md).

## Поиск по CSV

Кнопка **«Добавить CSV»** обрабатывает строки с описаниями товаров и показывает результат
для каждой строки. По умолчанию товар и код КТРУ отображаются только при заполнении
всех обязательных параметров; второй режим разрешает неполные товары с предупреждением.
Неопределённые КТРУ остаются отдельными плашками без кода. **«Выгрузить CSV»** сохраняет
все исходные строки и результаты с учётом переключателя.
[Формат файла и правила выгрузки](docs/CSV_IMPORT.md).
