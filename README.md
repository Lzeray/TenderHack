# Подбор КТРУ по описанию товара (TenderHack, MVP)

**Текущий пользовательский режим — живой двухветочный поиск:** [docs/LIVE_SEARCH.md](docs/LIVE_SEARCH.md).
При вводе автоматически извлекаются предмет/свойства, показываются все подходящие позиции КТРУ и
товары из XLSX. Qwen дополняет результат после паузы; обязательного предварительного выбора типа нет.
Запуск: `RECOGNITION_MODE=hybrid SEMANTIC=1 LLM_MODE=always`.

Веб-приложение: русскоязычное описание одного товара → нормализованные характеристики →
совместимые позиции КТРУ → уточняющие вопросы → конечный код.
Направления: одежда, мебель, инструменты.

Режим `rules` — детерминированная базовая линия: словарный разбор, OpenSearch или BM25, проверки на `Decimal`.
Добавлен экспериментальный `RECOGNITION_MODE=semantic`: поиск rubert-tiny2 при наборе, локальная Qwen после Enter,
подтверждение интерпретаций и то же ядро. В нём алиасы, SymSpell и главное слово не обязательны.
**Запуск, актуальные измерения и ограничения:** [docs/SEMANTIC_PIPELINE.md](docs/SEMANTIC_PIPELINE.md).
**Подготовка XLSX:** [docs/STE_DATA.md](docs/STE_DATA.md), отдельная база `data/ste.sqlite`.

## Быстрый старт (локально, Python 3.12)

```bash
pip install -r requirements.txt
# 1. Импорт: каталог с вложенными zip выгрузки nsiKTRUNew (not-actual пропускаются автоматически)
python -m ktru_assist.cli import --src "КТРУ/КТРУ xml/КТРУ" --db data/ktru.sqlite --as-of 2026-10-09
# 2. Запуск API + веб-интерфейса (встроенный BM25-поиск)
python -m ktru_assist.cli serve --port 8000        # http://127.0.0.1:8000
# 3. Тесты и оценка
python -m pytest -q
python -m eval.run_eval --repeat 20                                  # кейсы разработки
python -m eval.run_eval --cases eval/holdout.jsonl --out reports/holdout_results.json
```

`--src` принимает каталог, отдельный zip (в том числе с вложенными zip) или XML.
Если исходный архив ещё не распакован, можно передать `"КТРУ/КТРУ xml.zip"` напрямую.

## Docker Compose (с OpenSearch)

```bash
docker compose --profile setup run --rm importer      # XML → data/ktru.sqlite
docker compose up -d opensearch
docker compose --profile setup run --rm indexer       # SQLite → индекс OpenSearch
docker compose up -d app                              # http://localhost:8000
```

> не запускались. Все замеры ниже сделаны со встроенным бэкендом `local-bm25`
> (`SEARCH_BACKEND=local`, по умолчанию). Бэкенд указывается в каждом ответе API.

Переменные окружения: `KTRU_DB`, `SEARCH_BACKEND` (`local` | `opensearch`), `OPENSEARCH_URL`,
`OPENSEARCH_INDEX`, `TOP_K` (50), `TYPE_FETCH_LIMIT` (1000).

| Единицы | `units.py` | ОКЕИ → размерность, точный перевод внутри размерности |

| API/UI | `api.py`, `web/` | FastAPI и HTML/CSS/JS |

### Ключевые правила

- **Область проверки.** Поиск (top-K) используется только для того, чтобы определить тип товара — главное слово наименования.
  Затем из индекса берутся **все** активные позиции этого типа. Совпадение проверяется в этой полной области;
  если она обрезана лимитом, `matched` не выдаётся.
- **Тип по наименованию.** Если все слова наименования позиции есть в описании, область сужается до этого
  наименования. Это отдельный этап сужения, он виден в ответе.
- **Привязка значения к свойству** — только однозначная: по названию свойства рядом со значением, по единственному
  свойству нужной размерности или по значению из справочника. Иначе признак помечается `ambiguous`
  и предлагаются варианты.
- **Единицы.** 75 см = 750 мм, 0,5 кВт = 500 Вт. Вольты с ваттами не сравниваются: в этом случае проверка
  возвращает `invalid` с пояснением «несовместимая размерность».
- **Границы диапазонов** сохраняются из XML (`greater` / `greaterOrEqual`, `less` / `lessOrEqual`) и учитываются
  точно; смежные диапазоны объединяются только при общей точке.
- **unknown ≠ valid.** Отсутствие свойства у позиции даёт `unknown`; учитывается признак `noNewFeatures`.
- **`matched`** выдаётся, только если:
  - ровно одна активная конечная позиция (не шаблон);
  - тип подтверждён;
  - область проверена полностью;
  - нет неоднозначностей;
  - все обязательные свойства этой позиции подтверждены.
- **Ранжирование** не является вероятностью. Ключ сортировки: уровень совпадения наименования → доля слов
  наименования → покрытие терминов запроса → число проверенных условий → число непроверенных → код КТРУ.
- **Уточнения.** Для каждого незаданного свойства (и для «типа») считается, сколько кандидатов останется
  при каждом варианте ответа; пересекающиеся значения учитываются. Выбирается вопрос с минимальным
  худшим случаем. При равенстве первым идёт тип, затем обязательное свойство, затем код свойства.
  Если ни один вопрос не сокращает набор, предлагается ручной выбор.
- **Ручная правка** (`overrides`) приоритетнее текста: извлечённое значение помечается `overridden`.
- **Ответы на уточнения** привязаны к хешу текста: после изменения описания они не применяются
  (предупреждение `stale_answers`).

## API

- `POST /api/search` — `{text, overrides[], answers[], answers_query_hash, corrections{}, top_k}`.
  В ответе: `status` (`matched` | `clarification_needed` | `conflict` | `not_found` | `manual_choice`),
  `message`, `corrections`, `features`, `unrecognized`, `candidates` (с `checks` и `rank_components`),
  `stages`, `question`, `final_code`, `issues`, `completeness`, `versions`, `elapsed_ms`.
- `GET /api/catalog` — версия снимка, дата применимости, покрытие категорий, счётчики импорта.
- `GET /api/positions/{code}` — позиция со всеми характеристиками.
- `GET /health`.
- Интерактивная документация: `/docs` (FastAPI).

**Импорт.** 82 actual-файла, 81 465 записей → 81 463 позиции (2 записи — более ранние версии), около 46 с.

| Мебель | 224 | 83 |

**pytest:** 45 тестов проходят. Из них 41 — на синтетическом каталоге-fixture (`tests/fixture_ktru.py`, явно помечен),
4 — smoke-тесты на реальной базе.

**Оценка на вручную размеченных кейсах.** Эталон для каждого кейса взят из значений характеристик в каталоге,

Симуляция ответов на уточнения: «пользователь» выбирает вариант, совместимый с эталоном. Все кейсы,
где сразу был задан вопрос, дошли до верного кода за 1–3 вопроса (6/6 и 3/3).

Задержка `engine.search` на кейсах разработки (560 вызовов): p50 14,6 мс, p95 41 мс, максимум 221 мс.
Через HTTP API (TestClient, 140 вызовов): p50 25 мс, p95 48 мс. Инициализация движка — около 1,4 с.

**Ограничения оценки (важно):**
- **Кейсы разработки** — не независимая оценка: я размечал их параллельно с разработкой и исправил по ним
  одну ошибку (выбор ближайшего вхождения слова).
- **Отложенный набор** размечен до первого запуска на нём и не правился, но автор тот же.
  Формулировки близки к наименованиям КТРУ, поэтому качество на реальных описаниях поставщиков
  (например, из `Примеры выгрузок/*.xlsx`) **не измерено**.
- **Выборки маленькие** (46 кейсов) и не случайные. Метрики показывают поведение на этих кейсах,
  а не долю ошибок в генеральной совокупности.
- **Задержки** измерены в одном процессе на ноутбуке разработчика. Нагрузочное тестирование и
  замер памяти не проводились.

## Что не проверено

- **OpenSearch-бэкенд и Docker Compose** — Docker не было на машине разработки.
- **Веб-интерфейс:** проверено, что страница и скрипт отдаются сервером и что синтаксис JS корректен (`node --check`).
  Автоматического браузерного теста нет.
- **Excel-выгрузки СТЕ** использованы только для изучения структуры. Алиасы составлены вручную и
  проверены по каталогу: тест `test_aliases_point_to_existing_heads`.

## Известные ограничения MVP

- Тип товара определяется по главному слову наименования КТРУ. Синонимы типа — только из
  `data/aliases.json` (например, «болгарка» не распознаётся).
- Габариты «120x60x75 см» без названий измерений не привязываются: признак `ambiguous`, свойство
  выбирает пользователь.
- Не все словоформы значений распознаются: «сетевой» ≠ «От сети», «раскладной» ≠ «Наличие механизма
  раскладывания». В таких случаях система задаёт вопрос, а не угадывает.
- Один товар на запрос. Подбор коммерческих СТЕ не реализован.
