## 1. Задача (исходная постановка пользователя)

Рабочий MVP для TenderHack: автозаполнение унифицированных характеристик и подбор
конечного кода КТРУ по русскоязычному описанию товара.

Сквозной сценарий: описание товара → нормализованные характеристики → совместимые
позиции КТРУ → уточнения → конечный код. Категории MVP: одежда, мебель, инструменты.

Ограничения:

- Linux и веб-интерфейс.
- Без внешних API проприетарных LLM, платных поисковых API и low-code/no-code.
- В первой версии без RAG, LLM, embeddings и нейросетевого ранжирования
  (это отменяет LLM/RAG-подход из `PROJECT_IDEA.md` и `IMPLEMENTATION_PROMPT.md`).
- Решения объяснимые и воспроизводимые.

Стек: Python, FastAPI, Pydantic, OpenSearch, SQLite read-only, pytest, Decimal для чисел,
интерфейс на HTML/CSS/JavaScript.

Независимые модули: импорт каталога, нормализация запроса, исправление опечаток,
извлечение характеристик, поиск кандидатов, валидация, ранжирование, выбор уточнений, API.

Импорт: обрабатывать actual, игнорировать not-actual; сначала выбрать последнюю версию
позиции, затем проверять статус и сроки; сохранять обязательность свойств, ОКЕИ,
допустимые значения, диапазоны, включённость границ, родительские связи, признак шаблона;
объявить покрытие категорий и версию снимка.

Обработка запроса:

1. Сохранить исходный текст и историю преобразований.
2. Нормализовать регистр, пробелы, словоформы; сохранить отрицания, числа, единицы,
   коды и модели.
3. Опечатки исправлять по словарю каталога только при однозначном соответствии; при
   нескольких вариантах — предлагать выбор; числа и единицы нечётко не исправлять.
4. Извлекать тип товара, качественные значения, числа, единицы, отрицания и
   конструкции «характеристика: значение».
5. Привязывать значение к свойству только при однозначном соответствии;
   нераспознанные значимые фрагменты возвращать явно.
6. Ручное редактирование приоритетнее текста; переопределение показывать.

Поиск: OpenSearch даёт кандидатов по названию, словоформам и проверенным алиасам;
проверка характеристик — отдельный модуль; ограничения пользователя автоматически
не ослаблять.

Валидация: для каждого свойства каждого кандидата — `valid` / `invalid` / `unknown`.
Проверять размерность, допустимые значения, диапазоны, обязательность, конфликтующие
условия. Точный перевод единиц (75 см = 750 мм), В не подменять на Вт, учитывать
запрет дополнительных характеристик. `unknown` не считается `valid`.

Ранжирование: после исключения несовместимых — фиксированный ключ: качество совпадения
названия/типа, покрытие значимых терминов, проверенные условия, непроверенные условия,
код КТРУ. Показывать компоненты. Не называть score вероятностью.

Уточнения: вопросы по шаблонам и реальным схемам оставшихся кандидатов; выбирать
свойство, сильнее сокращающее множество в худшем случае; учитывать пересекающиеся
допустимые значения; при равенстве — обязательное свойство, затем код свойства; если
свойства не разделяют позиции — уточнять тип товара или предлагать ручной выбор.

Конечный код: `matched` только для одной активной конечной позиции в полностью
проверенной области, при заполненных обязательных полях и без блокирующих проблем.
Шаблон — не конечный результат. Единственный результат в ограниченном top-K
не доказывает уникальность.

API: `POST /api/search`, `GET /api/catalog`, `GET /api/positions/{code}`, `GET /health`.
Ответ: статус, исправления, извлечённые характеристики, кандидаты с объяснениями,
ошибки, этапы сужения, уточняющий вопрос, конечный код, версии компонентов, признаки
полноты поиска.

UI: русский язык, описание с debounce, редактируемые характеристики, единицы и статусы
проверки, кандидаты, реальные количества оставшихся позиций, вопросы с вариантами,
объяснения ошибок, экспорт JSON. Референс дизайна — https://zakupki.mos.ru/ или
Figma-доска «Portal Postavshikov (catalog)».

Тесты: импорт версий, опечатки, неоднозначность, отрицания, несовместимые единицы,
диапазоны с открытыми границами, неполные данные, неизвестные свойства, ручное
редактирование, шаблоны, ограниченный поиск, повторяемость. Плюс независимые вручную
проверенные кейсы, реальные замеры задержек и качества. Каталожные smoke-тесты
не называть независимой оценкой точности.

Результат: исходники, Docker Compose, команды импорта и запуска, README, тесты,
реальные результаты проверок, BPMN-схема.

### Характеристика (`characteristics/characteristic`)

| Поле | Значения |
| --- | --- |
| `code`, `name` | код вида `ee94fa19-1`; одинаковый код у одной характеристики в разных позициях семейства |
| `type` | `1` качественная, `2` количественная |
| `kind` | `1` неизменяемая заказчиком, `2` изменяемая с выбором одного значения, `3` изменяемая с выбором нескольких |
| `isRequired` | `true` / `false` |
| `choiceType` | `1` единственный, `2` множественный, `3` неизменяемый (по описанию — для ведения КТРУ, не для применения) |
| `actual` | в данных всегда `true` |

Значение (`values/value`) бывает трёх видов:

1. `qualityDescription` — текст («Да», «Нет», «Сталь», «Слесарные»).
2. `OKEI` + `valueFormat` + `rangeSet/valueRange` — диапазон. `min` и `max` могут
   отсутствовать по отдельности (открытый диапазон). Границы:
   `minMathNotation` ∈ {`greater`, `greaterOrEqual`}, `maxMathNotation` ∈ {`less`, `lessOrEqual`}.
   Типичный ряд: `< 160`, `≥ 160 и < 180`, `≥ 180 и < 200` … — смежные полуоткрытые
   интервалы, поэтому включённость границы решает, в какой интервал попадает число.
3. `OKEI` + `valueFormat` + `valueSet/concreteValue` — конкретное число.

Особенности:

- `OKEI` у числового значения может отсутствовать: единица зашита в названии
  («Максимальный крутящий момент (Нм)») либо значение — условный номер
  («Исполнение» = 1 / 2). Такие числа нельзя сопоставлять по единице.
- `valueFormat`: `N` почти всегда, `A` (дополнительный) — редко.
- `valueCode` отсутствует у небольшой доли значений.
- Числа — `N(14,4)`, читать как Decimal из строки.

### Устройство семейства позиций

Пример «Пассатижи» (`25.73.30.163`): шаблон `…-00000019` (`isTemplate=true`, без
родителя) и конечные позиции `…-00000001…` с `parentPositionInfo` на шаблон.

- Конечные позиции различаются характеристикой `kind=1`, `isRequired=true` с одним
  значением («Вид пассатижей»: Переставные / Рыбацкие / Зажимные / Слесарные …).
- У шаблона та же характеристика содержит все варианты сразу.
- Остальные характеристики (`kind=2/3`) одинаковы по семейству и задают допустимые
  значения/диапазоны, которые выбирает заказчик («Длина», «Режущие кромки»).

Следствие для алгоритма: конечный код определяют в основном `kind=1`-характеристики;
`kind=2/3` служат для проверки значений и редко разделяют позиции. Вопрос-уточнение
должен выбираться по реальному разбиению оставшихся кандидатов, а не по обязательности.

Другие примеры: «Стул на металлическом каркасе» (`31.01.11.150`) — позиции различаются
парой «Наличие мягкого сидения» / «Наличие мягкой спинки»; «Шуруповерт»
(`28.24.11.000`) — «Тип питания»; «Молоток» (`25.73.30.141`) — «Тип».

### Критерии категорий MVP

Рубрикаторы в данных есть, но отдельной рубрики «Инструменты» нет:

| Категория | Критерий | Обоснование |
| --- | --- | --- |
| Одежда | ОКПД2 `14.*` | рубрика 116 «Одежда и обувь» покрывает её, но включает и обувь `15.20`; часть `14.12` лежит в рубрике «Медицинские изделия» |
| Мебель | ОКПД2 `31.*` | почти всё в рубрике 128 «Мебель» |
| Инструменты | ОКПД2 `25.73.*` и `28.24.*` | `25.73` разбросан по рубрикам «Строительные материалы», «Прочее» и др.; `28.24` — «Электрическое оборудование» |

Решение: отбирать по префиксу ОКПД2, рубрику сохранять как справочное поле.
Включать ли обувь `15.20` в «одежду» — открытый вопрос, по умолчанию не включена.

Активные позиции в просмотренной части: `14.*` — около 760 (из них шаблонов ~70),
`31.*` — около 260 (шаблонов ~80), `25.73` — 155 (шаблонов 31), `28.24` — 36
(шаблонов 11). В группах много позиций «Услуги по производству…» и позиций,
дублирующих название класса ОКПД2, без характеристик.

## 4. Команды для пользователя (PowerShell)

Проверить, есть ли среди вложенных архивов выгрузки `not_actual`:

```powershell
cd "C:\Users\Matvey\ThenderHack\КТРУ\КТРУ xml\КТРУ"
Add-Type -AssemblyName System.IO.Compression.FileSystem
$bad = Get-ChildItem *.zip | Where-Object {
  $z = [IO.Compression.ZipFile]::OpenRead($_.FullName)
  $hit = @($z.Entries | Where-Object { $_.Name -match 'not[_-]?actual' }).Count -gt 0
  $z.Dispose(); $hit
}
$bad | Select-Object Name
```

Если список не пуст — удалить их (безвозвратно, мимо корзины):

```powershell
$bad | Remove-Item
```

Распаковать вложенные архивы в XML (необязательно — импортёр будет читать zip напрямую):

```powershell
Get-ChildItem *.zip | ForEach-Object { Expand-Archive $_.FullName -DestinationPath ..\xml -Force }
```
