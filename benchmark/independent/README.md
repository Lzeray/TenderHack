# Независимые наборы и метрики v2

> **С 10.10.2026 в репозитории оставлена только test-часть `natural` (313 кейсов).** Ниже — описание построения
> всего набора v2; удалённые части есть в истории git. Актуальный запуск — `benchmark/README.md`.

Зачем это нужно. Старые наборы (`benchmark/suites`) писал тот же разработчик, что и систему, и по ним же
шла отладка. Метрика там слабая: решение, которое всегда задаёт уточняющий вопрос, получает на синтетике
99,5% pass_rate. Здесь наборы и метрики построены без опоры на поведение системы.

- Эталон считается своим кодом прямо из `data/ktru.sqlite`. Это файл `reference.py`: собственные интервалы,
  единицы и сравнение значений, все числа в `Decimal`. Из `ktru_assist` берётся только чтение xlsx
  (`ktru_assist.portal.xlsx`) — и только для шаблона ручной разметки.
- При построении наборов логика системы не читалась, а сама система на них не запускалась.
- В отчёт всегда входят тривиальные базовые линии. По ним видно, какой минимум получает решение,
  которое вообще ничего не делает.

## Как устроен эталон

В каждом кейсе тип товара назван наименованием позиции КТРУ: точным или в естественной форме — в нижнем
регистре, в родительном падеже («закупка пассатижей») или с переставленным прилагательным («ручная пила»).
В поле `facts` перечислено всё, что заявлено в тексте: свойство (точное имя характеристики КТРУ),
значение, единица (как она написана в тексте), оператор `=`, `>=` или `<=`.

`gold_codes` — это все активные конечные позиции (`active=1`, `is_template=0`, категория clothes, furniture
или tools) с этим наименованием, у которых для **каждого** факта есть характеристика с таким же именем,
и её допустимые значения совместимы с фактом.

Как проверяется совместимость (`reference.py`):

- **Текстовый факт.** Совместим, если среди значений характеристики есть качественное с тем же текстом.
  Регистр, ё/е, лишние пробелы и точки по краям не учитываются. Опечатки эталон не исправляет: факт хранит
  правильное значение, а опечатка есть только в тексте.
- **Числовой факт.** Совместим, если хотя бы одно допустимое значение подходит после точного перевода
  единиц. Значение — это конкретное число или диапазон с учётом включённости границ `min`/`max`.
  Факт `>=`/`<=` совместим, если его луч пересекается с диапазоном.
- **Перевод единиц.** Работает только внутри одной величины: мм/см/м/км/дюйм, г/кг, Вт/кВт.
  Разные величины (В и Вт, кг и Вт, мм и кг) несовместимы никогда.
- **Факт без единицы.** Сравнивается с числом каталога в единице каталога.
- **Факт с единицей при значении без ОКЕИ.** Несовместим: единицу проверить нельзя.

Поле `expect` вычисляется из `gold_codes` и фактов, а не задаётся вручную:

| `expect` | Условие |
|---|---|
| `code_required` | В эталоне ровно одна позиция, и в тексте заявлены все её характеристики с `kind=1` и все обязательные (`is_required`). Код должен выдаваться сразу, без вопросов. |
| `code_after_questions` | Эталон непуст, но код однозначно не определяется (позиций больше одной) или заявлены не все обязательные характеристики. |
| `no_code` | Эталон пуст: противоречие, значение вне каталога, несовместимая единица или товар вне трёх направлений. |

Тест `test_suites_gold_matches_catalog_and_manifest` пересчитывает `gold_codes` и `expect` каждого кейса
по базе и сверяет их с файлами.

## Формат кейса

Кейс хранится в JSONL. Поля совместимы с `benchmark/README.md`: `id`, `suite`, `split`, `text`,
`acceptable_codes` (равно `gold_codes`), `auto`, `expected_status`, `forbidden_codes`, `checks`.

Поля v2:

- `gold_codes` — список кодов эталона;
- `expect` — `code_required`, `code_after_questions` или `no_code`;
- `facts` — что заявлено в тексте;
- `variant` — схема построения и приёмы через `+`.

Служебные поля: `name` (наименование позиции), `category`, `target_code` (позиция, по которой строились
факты; она всегда входит в эталон), `typo` (какое слово искажено), `item` (для `out_of_scope`).

Схемы построения в `variant`: `full`, `full_extra`, `full_rephrased`, `partial`, `bare`, `kind1_conflict`,
`unit_mismatch`, `out_of_range`, `out_of_scope`.

Приёмы в `variant`: `genitive`, `name_swap`, `noise`, `typo`, `negation`, `unit_conversion`, `inequality`.

## Наборы

Сплит dev/test делается по sha256 от наименования позиции с солью `iv2-a`. Все варианты одного наименования
попадают в один сплит во всех наборах. Соль выбрана из семи кандидатов только по тому, насколько доля test
близка к 30%. Решения при этом не запускались.

| Набор | Всего | `code_required` dev / test | `code_after_questions` dev / test | `no_code` dev / test |
|---|---|---|---|---|
| `natural` | 1073 | 472 / 189 | 288 / 124 | 0 / 0 |
| `contradictions` | 343 | — | — | 241 / 102 |
| `out_of_scope` | 98 | — | — | 66 / 32 |

**natural.** Для каждого наименования берутся до 4 позиций (все, если их не больше 4). Варианты:

- `full` — все `kind=1` и все обязательные характеристики позиции, иногда ещё 1–2 необязательные;
- `full_rephrased` — те же характеристики другими словами;
- `partial` — без одной из обязательных характеристик;
- `bare` — одно наименование, иногда с одним необязательным свойством.

Как построены формулировки:

- **Свойство и значение без двоеточия** — в большинстве кейсов. Конструкция «свойство: значение» есть
  только в 11% кейсов.
- **Значения-прилагательные согласуются с наименованием через pymorphy3**: «рыбацкие пассатижи»,
  «закупка пассатижей рыбацких».
- **Числа — с творительным падежом свойства**: «длиной 18 см», «мощностью 0,6 кВт».
- **Да/Нет**: «с мягким сиденьем», «без подлокотников», «воротник отсутствует», «кожа не натуральная»,
  «не диэлектрические».
- **Материалы**: «спинка из пластика».
- **Значения с предлогом**: «от сети».
- **Разные написания единиц и перевод между ними**: мм / миллиметров / см / метра, Вт / кВт.
- **Перестановки фактов** и разные зачины: «нужны …», «требуется …», «закупка …», «подберите КТРУ: …».
- **Шум**: бренд, «производство Россия», артикул.
- **Опечатка в одном словарном слове** длиннее 4 букв — примерно в 20% кейсов. Числа и единицы не
  искажаются, а искажённое слово проверяется на отсутствие в словаре.

**contradictions.** Все кейсы — `no_code`, к каждому добавлена проверка `warning`. Чтобы противоречие было
единственной причиной отказа, к нему добавлены остальные обязательные характеристики позиции.

- `kind1_conflict` — два разных значения одной характеристики `kind=1` у одного наименования:
  «с мягкой спинкой, нет мягкой спинки», «тип питания — от сети; тип питания — от аккумулятора».
- `unit_mismatch` — физически несовместимая единица: «рост 164 кг», «мощность 200 кг», «шаг резьбы 2,5 Вт».
- `out_of_range` — число вне объединения всех допустимых значений семейства. Берётся втрое выше
  максимальной верхней границы или вчетверо ниже минимальной нижней.

В `forbidden_codes` лежат «соблазнительные» позиции — те, что подошли бы без противоречия.

**out_of_scope.** Товары вне трёх направлений: бытовая техника, канцелярия, продукты, обувь, стройматериалы,
электроника и т. п. Тип товара отбрасывается, если его существительное совпадает с лексемой любого
наименования каталога (например, «телевизор» из-за «Тумба под телевизор»).

## Метрики (`metrics.py`)

Все метрики считаются отдельно по каждому набору и для каждого решения.

| Метрика | Определение |
|---|---|
| `wrong_auto` | Решение выдало код сразу (`status=matched`), а код ∉ `gold_codes`. Сюда же — любой код при пустом эталоне. В отчёте число и доля среди автокодов. |
| `auto_precision` | 1 − `wrong_auto` / число автокодов |
| `auto_coverage` | Число автокодов / все кейсы |
| `code_reached@0` | Среди кейсов с непустым эталоном — доля, где верный код выдан сразу |
| `code_reached@k`, k = 1, 2, 3 | Верный код получен не более чем за k уточнений через `adapter.dialog(text, set(gold), max_steps=3)` |
| `required_hit` | Среди `code_required` — доля, где верный код выдан сразу |
| `no_code_respected` | Среди `no_code` — доля, где код не выдан |
| `premature_auto` | Среди `code_after_questions` с несколькими позициями в эталоне — доля автокодов, то есть угадываний (справочно) |
| `questions_mean` | Среднее число вопросов до верного кода. Считается по кейсам, где код получен за ≤ 3 шага; 0 — если код выдан сразу. |
| `dialog_wrong_final` | Диалог закончился кодом не из эталона |
| `latency_ms_p50`, `latency_ms_p95` | Задержка `predict` |
| `over_asking` | Среди `code_required` — доля, где решение спросило вместо кода |
| `wrong_auto_gold_listed` | Ошибочный автокод, хотя эталон был в списке решения: подвело ранжирование, а не разбор |
| `ranking.*` | `hit@1/@3/@5`, `mrr`, `ndcg@3`, `type_hit@1`, `rank_by_step`, `hit1_by_step`, `mrr_by_step`, `questions_to_top1_mean`, `bits_per_question`, `useless_question_rate`, `dead_end_rate`. Определения — в `benchmark/README.md` и `benchmark/ranking.py`. Для `hit@1` и `hit@3` считаются 95% интервалы |

Как считаются `code_reached@k`:

- `dialog` вызывается один раз с `max_steps = max(k)`, а значение @k берётся по числу сделанных шагов
  (`steps ≤ k`). Для детерминированного диалога, который останавливается на первом коде, это то же самое,
  что отдельный вызов с `max_steps=k`.
- Если код уже выдан сразу и верно, диалог не вызывается.
- Если адаптер не умеет `dialog` (возвращает `None`), то @k = @0, и в отчёте ставится пометка
  `not_supported`.

95% доверительные интервалы есть для `code_reached@2`, `auto_precision` и `no_code_respected`.
Это перцентильный бутстреп: 2000 повторов (минимум 1000), seed 20261010. Если ошибок нет (доля = 1),
нижняя граница равна 1 − 3/n по правилу трёх; если успехов нет, верхняя граница равна 3/n.
`wrong_auto_rate_upper95` = 1 − нижняя граница `auto_precision`.

**Пол метрик.** Отчёт всегда включает две тривиальные линии: `baseline:always_clarify` и
`baseline:always_not_found`. Они получают `no_code_respected = 1` и `wrong_auto = 0`, но `code_reached@k = 0`
и `required_hit = 0`. Поэтому решение оценивается только по паре метрик — например, `code_reached@2` на
`natural` вместе с `no_code_respected` на `contradictions` и `out_of_scope` и с `wrong_auto`. Ни одна метрика
по отдельности ничего не доказывает.

## Запуск

```bash
python -m benchmark.independent.generate --stats          # распределение без записи
python -m benchmark.independent.generate                  # пересобрать suites/ (test-часть сверяется с манифестом)
python -m benchmark.independent.run --adapters ktru:core \
    --suites natural contradictions out_of_scope --out reports/bench/independent/v2.json
python -m benchmark.independent.run --adapters ktru:core --split dev      # настройка — только на dev
python -m benchmark.independent.run --adapters ktru:core --split test --hide-test-cases
python -m benchmark.independent.make_labeling              # → benchmark/local_suites/labeling_template.csv
python -m pytest -q tests/test_independent_metrics.py
```

Адаптеры задаются так же, как в `benchmark.run`: `ktru:core`, `ktru:core_sem_b`,
`ktru_http:http://127.0.0.1:8000`, `модуль:Класс=аргумент`. Можно указать несколько адаптеров сразу.

Другие ключи:

- `--no-dialog` — не вызывать `dialog`;
- `--ks 1 2 3` — шаги для `code_reached@k`;
- `--bootstrap N` — число повторов бутстрепа, N ≥ 1000;
- `--no-baselines` — без тривиальных базовых линий;
- `--limit N` — первые N кейсов каждого набора, для отладки.

## Заморозка test

`test_manifest.sha256` хранит sha256 test-части каждого набора: точные строки файла со `split=test` в
порядке файла. `run.py` при каждом прогоне сверяет хеши и пишет результат в `meta.frozen` и в шапку
Markdown. Тест сверяет их тоже. Подробности — в `FROZEN.md`.

Правила:

1. Разработчики смотрят по test **только агрегаты**: таблицы `run.py`, блок `by_split.test`. Отдельные
   test-кейсы не разбираются, тексты test-кейсов не читаются, система под них не настраивается.
   Для прогонов по test есть `--hide-test-cases`.
2. Вся настройка (алиасы, правила, пороги, словари) делается только на dev и на собственных примерах.
3. Если test-часть пришлось изменить (новый импорт КТРУ, исправление генератора), это новая версия
   наборов (v3) с новым манифестом и записью в `FROZEN.md`. Результаты разных версий не сравниваются.

## Ручная разметка

`make_labeling.py` выбирает 300 случайных карточек портала — по 100 на категорию, seed фиксирован,
выборка резервуарная. Результат пишется в `benchmark/local_suites/labeling_template.csv` в кодировке UTF-8
с BOM. Папка в `.gitignore`: это данные организаторов, коммитить их нельзя.

Колонки:

- `id` — ID СТЕ;
- `category`;
- `text` — наименование карточки и две её характеристики, без «(не задано)», ссылок, нулевых заглушек
  и хвостов «.00000»;
- `gold_code`, `alternatives`, `expect`, `comment` — заполняет команда.

Инструкция для разметчика:

1. **Сначала проверьте, в области ли товар.** Найдите позицию КТРУ в справочнике (zakupki.gov.ru, раздел
   КТРУ, или `tools/family.py`). Товары вне одежды (ОКПД2 `14.`), мебели (`31.`) и инструментов (`25.73`,
   `28.24`) получают `expect = no_code`, `gold_code` остаётся пустым. Например, сандалии — это обувь `15.20`.
2. **`gold_code`** — одна активная конечная позиция (не шаблон), которой текст соответствует по всем
   заявленным характеристикам. Код решения при этом не смотреть.
3. **`alternatives`** — другие позиции, которые тоже совместимы с текстом, через `;`. Если позиций
   несколько, `gold_code` оставьте пустым и перечислите их все в `alternatives`.
4. **`expect`** проставляется по правилам эталона:
   - `code_required` — текст однозначно указывает на одну позицию, и в нём есть все её `kind=1`
     и обязательные характеристики;
   - `code_after_questions` — подходящая позиция есть, но для выбора нужны уточнения;
   - `no_code` — вне области, противоречие или значение, которого нет в КТРУ.
5. **`comment`** — сомнения, причина `no_code`, ссылки на характеристики КТРУ.
6. **Каждую строку размечают два человека независимо**, расхождения разбираются вместе. Долю совпадений
   до разбора стоит записать: это оценка надёжности самой разметки.
7. **Размеченный файл не превращается в настройки системы.** Он делится на dev/test так же, как наборы
   выше, и test-часть замораживается.

## Известные ограничения

Что всё ещё не является независимой оценкой:

- **Синтетика остаётся синтетикой.**
  - Тексты собраны из имён и значений каталога. Набор `natural` проверяет разбор формулировок, морфологию,
    единицы, отрицания, шум и опечатки. Но он не проверяет, как пишут реальные заказчики: сокращения,
    жаргон, свойства, которых нет в КТРУ, лишние сведения, перепутанные свойства.
  - Реальную точность покажет только ручная разметка карточек портала (`labeling_template.csv`).
- **Эталон привязан к семейству наименования.**
  - Близкие позиции других наименований в эталон не входят. Например, для «шапка зимняя» не засчитываются
    «Головные уборы» с видом «Шапка», а для «брюки» — «Брюки спортивные». Решение, которое выбрало такую
    позицию, получит `wrong_auto`, хотя человек мог бы с ним согласиться.
  - Синонимы типа («плоскогубцы» вместо «пассатижи») не генерируются.
- **Свойство с единицей при значении каталога без ОКЕИ** эталон считает несовместимым. Таких диапазонов
  в базе около 280. Генератор не ставит единицу у чисел без ОКЕИ: единица берётся только из
  имени свойства («Свинцовый эквивалент, мм Pb»).
- **«Обязательные» характеристики — это флаг `is_required` из КТРУ.** Нужно ли требовать их все для
  автокода (`code_required`), решила команда, и это можно оспорить. При другом решении часть кейсов
  перейдёт из `code_after_questions` в `code_required` и обратно.
- **Морфология pymorphy3 не идеальна.** Если надёжного разбора нет, генератор берёт нейтральную формулировку
  («свойство — значение»). Отдельные неуклюжие фразы всё же встречаются, например «размер 0,6 м» для
  головного убора после перевода из сантиметров.
- **Опечатка может попасть в значение или наименование.** Эталон считает, что пользователь имел в виду
  правильное слово. Если решение по правилам команды не исправляет опечатки, такие кейсы для него
  становятся `code_after_questions`.
- **`out_of_scope` и `contradictions` проверяют только отказ от кода.** Правильность объяснения (warning)
  проверяется слабо: проверка `warning` есть только в формате совместимости.
- **В `dialog` пользователь — «оракул»**: он выбирает вариант, совместимый с эталоном. Поэтому
  `code_reached@k` — верхняя оценка для настоящего пользователя.
- **Наборы не проверены людьми целиком.** Пока генератор отлаживался, автор просмотрел около 110 случайных
  кейсов из обоих сплитов — это было до заморозки. После заморозки просматривались только dev-кейсы.
