# Контракты, статусы и правила завершения

Документ описывает фактический код (`ktru_assist/models.py`, `engine.py`, `resolver.py`, `orchestrator.py`).
Названия разделов плана — в `docs/PLAN.md`.

## Запрос `POST /api/search` (`SearchRequest`)

| Поле | Смысл |
| --- | --- |
| `text` | исходное описание (до 2000 символов) |
| `session_id`, `revision` | сеанс интерфейса и версия состояния; revision растёт при любом изменении ввода (текст, правка, ответ, подтверждение, отказ, Enter) |
| `stage` | `draft` — черновик A при вводе; `submitted` — Enter, допускает разбор B |
| `overrides` | ручные правки (приоритет над текстом); `remove=true` удаляет извлечённое значение |
| `answers`, `answers_query_hash` | ответы на вопросы; применяются, только если хеш лемм описания не изменился |
| `corrections` | выбор исправления опечатки |
| `rejected` | ключи отклонённых предложений моделей (`Proposal.key` / `Feature.proposal_key`) |
| `confirmed` | ключи подтверждённых предупреждений правдоподобия |

## Ответ (`SearchResponse`)

Прежние поля сохранены без изменения смысла (`status`, `features`, `candidates`, `stages`, `question`,
`final_code`, `issues`, `completeness`, `versions`). Новые:

| Поле | Смысл |
| --- | --- |
| `session_id`, `revision`, `run_id`, `stage` | служебная оболочка; при выдаче из кэша создаётся новая |
| `preliminary` | `true` для черновика |
| `stale` | сервер уже получил более новую revision этого сеанса — ответ не применять |
| `assertions` | исходные признаки (RawAssertion): источник, цитата с координатами исходного текста (code points, конец не включается), значение и единица как в тексте, оператор, отрицание, намерение (факт/требование/предпочтение), статус согласования |
| `features` | разрешённые признаки (ResolvedAssertion): свойство КТРУ, `origin` (rule/semantic/llm/manual), `confirmation` (confirmed/tentative), `component`, `canonical_key`, `supported_by`, `raw_span` |
| `proposals` | предложения моделей; применяются только после «принять» (уходят в `answers`) |
| `code_resolution` | `resolved` / `unconfirmed` / `multiple` / `none` / `conflict` + код и причина |
| `characteristics_completion` | обязательные свойства: заполнено / всего, не указано, не проверено |
| `scope` | `detected_types`, `type_basis`, `confirmed_scope`, `scope_complete`, `registry_complete` |
| `providers` | статус моделей: off / ok / skipped / timeout / error / invalid / cached / stale |
| `changes` | что изменил разбор B относительно черновика |
| `timings` | мс по этапам: normalize, retrieval, extract, validate, decide, semantic, llm, end_to_end |
| `effective_at` | дата проверки активности позиций (снимок) |

`GET /api/providers` — состояние моделей и закреплённые ревизии.

## Семантика `status` (совместима с MVP)

`matched` выдаётся, только если одновременно:

1. ответ относится к актуальной revision (иначе `stale=true`, клиент не применяет);
2. осталась ровно одна совместимая **конечная** позиция (не шаблон), активная на `effective_at`;
3. тип подтверждён: полное совпадение наименования, единственное наименование в области или выбор пользователя.
   Разговорное слово с несколькими трактовками (алиас-список) тип не подтверждает;
4. область типа проверена полностью (все активные позиции с этим главным словом, не top-K);
5. нет неоднозначных признаков и неоднозначных опечаток;
6. у позиции нет `unknown` по указанным свойствам и **заполнены все обязательные свойства**;
7. **нет неподтверждённых гипотез моделей** (`confirmation=tentative`), типа, предложенного моделью,
   неподтверждённых подозрительных значений и расхождений модели с правилами.

Пункты 1–6 — прежняя семантика MVP, пункт 7 — новая защита. `code_resolution=resolved` требует 1–5 и 7:
поэтому бывает «код определён однозначно, но обязательные характеристики СТЕ не заполнены»
(`status=clarification_needed`, `characteristics_completion.complete=false`).

Если выполнено всё, кроме п. 7, задаётся вопрос `kind=confirm`: «Да, всё верно» отправляет гипотезы
как `answers` и подтверждения как `confirmed`; варианты «Нет: …» добавляют ключ в `rejected`.

## Правила доверия (resolver.py)

1. Ручные правки и ответы — выше всего; модель с ними не спорит (её вариант отклоняется).
2. Однозначный разбор правилами не меняется моделью: при расхождении остаётся значение правил,
   расхождение — предупреждение `model_disagreement` и блокировка `matched` до подтверждения.
3. Совпадение модели с правилами записывается в `supported_by`.
4. Гипотеза модели, противоречащая всем конечным позициям области, не применяется как условие
   (`status=proposed`, предупреждение `model_value_not_in_ktru`): это сигнал об ошибке в описании.
5. Предпочтение («желательно …») не становится жёстким условием.

## Проверка ответа LLM (llm/extractor.py)

Применяется только ответ, прошедший все проверки:
JSON по схеме (`SCHEMA_HASH` в `versions.llm_schema`); `quote` — точная подстрока описания (с точностью до ё/е);
`property_ref` — из `allowed_property_refs` контекста; числа значения есть в цитате; единица есть в цитате;
качественное значение — допустимое значение КТРУ или слова пользователя. Сопоставление по смыслу
(«от розетки» → «От сети») принимается, только если в цитате есть слово значения/названия свойства
или слово, которое правила не разобрали. Невалидный или обрезанный ответ не применяется целиком;
один повтор — только при техническом сбое; таймаут и недоступность — честный черновик и ручной путь.

## Эскалация на B (orchestrator.escalation_reasons)

Только `stage=submitted` и `LLM_MODE=escalate|always`. Причины: неразобранные значимые слова;
неоднозначная привязка; свойство не найдено у типа; тип не найден или не подтверждён; конфликт,
не объяснимый ошибкой единицы; неоднозначная опечатка. Не вызывается ради ошибки размерности (В вместо Вт)
или незаполненного значения. `LLM_MODE=always` — режим проверки политики эскалации.

## Ключи кэша

| Слой | Ключ |
| --- | --- |
| Эмбеддинги каталога | ревизия энкодера + пулинг, снимок, все справочные строки (`data/cache/semantic_*.npz`) |
| A | запрос без session/revision/stage + все версии (правила, словари, модели) |
| B | промпт, схема, digest модели, параметры, полный текст и контекст (`context_id`) |

В кэш B попадает только валидный ответ. Revision в семантический ключ не входит.
