# Подбор только по КТРУ: тип, основные и неосновные характеристики, полнота выдачи

Постановка пользователя (10.10.2026): из строки извлекаются тип предмета, основные характеристики и неосновные.
По типу и характеристикам ищутся **все** подходящие позиции КТРУ. Пример проблемы: на «стол» выдавались
2 позиции из 31 конечной.

## Решения команды

1. Основная характеристика — обязательная (`isRequired`) хотя бы в одной позиции типа. Остальные — неосновные
   (их разделение на два вида — позже).
2. Отбор: позиция исключается, только если у неё есть названное свойство и значение ему противоречит.
   Позиция без свойства или с необязательным свойством остаётся (`unknown ≠ invalid`). Правило из `main`
   «характеристика обязательна в части позиций → остальные отбрасываются» снимается.
3. Неосновные характеристики, которые назвал пользователь, отбирают так же («стол деревянный» → исключаются
   позиции, где материал задан и дерева среди значений нет). Обязательные характеристики запрашиваются до
   конца: пока они не заполнены, код не выдаётся.
4. Значение пользователя совпадает со свойством, если оно есть среди допустимых значений позиции (одно из
   списка), а не только когда указан весь список.

## Шаги

- K0. Стенд `experiments/ktru_recall.py`: запросы из каталога (тип; тип + 1–2 основные; 1 неосновная;
  вперемешку; по главному слову и по наименованию), эталон по базе без кода движка.
- K1. «Вид товара» из слова типа сравнивается по главному слову: «стол» подходит «Стол для переговоров»,
  не подходит «Секция стола».
- K2. Снять правило отбора по «обязательна в других позициях».
- K3. Незаполненные обязательные характеристики снова не дают код.
- K4. Роль характеристики в ответе: основная / неосновная — по всем позициям типа.
- K5. Область поиска неполная («джинсы»): найти, почему позиции типа не попадают в область.
- K6. Ложная неоднозначность: «мужские» подходит к разным свойствам разных позиций.

## Журнал

Код выдан при незаполненных обязательных характеристиках: 120 запросов из 626. Пробы: «стол» — 2 позиции,
«шкаф» — 1.

Причины потерь (позиции эталона вне ответа): правило «обязательна в других позициях» — около 400;

Пересчёт эталона (после K1–K5): секция («Вид товара» с другим главным словом) не входит в тип, если вид товара не
назван; по наименованию подходят и более частные наименования с теми же словами. С новым эталоном база
пересчитана на коде `8d612e7` (`reports/exp/kr_base2.json`), таблицы ниже — по нему.

### K1–K6. Изменения

- K1 (`extractor` 2.3, `validator` 1.8): значение из слов наименования типа помечается `from_type_name` и
  сравнивается по главному слову: «Стол» подходит «Стол для переговоров», не подходит «Секция стола». Явно
  названный вид товара («вид товара: секция шкафа») важнее слова типа.
- K2 (`engine` 2.9): снят отбор «характеристика обязательна в части позиций → остальные отбрасываются».
- K3: незаполненные обязательные характеристики снова не дают код (правило «одна позиция = код» снято).
- K4: `Feature.role` — `main` / `other` по всем конечным позициям области до отбора. Сверка со стендом:
  310 привязанных характеристик из 310 — та же роль, 11 не привязаны.
- K5: к наименованиям, полностью названным в описании, добавляются более частные с теми же словами («Джинсы» →
  «Джинсы детские»). Тип подтверждён, если полностью названо одно наименование; если у оставшихся позиций разные
  наименования, задаётся вопрос о наименовании. Словами типа считаются только слова полностью названного
  наименования: иначе «металлический» из «Стул на металлическом каркасе» переставал быть характеристикой и
  противоречие «стул деревянный металлический» терялось (поймал `tests/test_query_conflicts.py`).
- K6: неоднозначное значение, чьи варианты-свойства не встречаются вместе ни в одной позиции («мужские» →
  «Половой признак» / «Назначение» / «Половозрастная группа»), проверяется по свойству, которое есть у позиции.
