# Трёхуровневая проверка характеристик товара: варианты и рекомендация

Oct 10, 2026 · @Madalyn

Рекомендация: статистику по выгрузкам СТЕ считать заранее и хранить в компактном артефакте SQLite, товары привязывать к типу КТРУ, а не к позиции, уровни 2 и 3 выдавать отдельными аннотациями, которые код проверки по КТРУ не читает.

## 1. Рекомендуемая архитектура

Система делится на офлайн-сборку и онлайн-проверку. Всё тяжёлое выполняется при импорте; на запросе остаются поиск по ключу и арифметика над Decimal.

**Офлайн-сборка** читает снимок КТРУ и базу выгрузок СТЕ и проходит пять стадий:

1. **Типы КТРУ.** Позиции группируются в типы по нормализованному наименованию и коду ОКПД2. Для типа строится каталог свойств: объединение характеристик семейства, каноническая единица, размерность.
2. **Очистка СТЕ.** Сегменты не удаляются, а получают флаги: заглушка, повтор, конфликт значений, упаковка, единица не определена.
3. **Привязка товара к типу.** Каскад: лексическое совпадение головного слова наименования, затем подтверждение по сигнатуре названий свойств. Значения свойств в привязке не участвуют.
4. **Сопоставление свойств.** Внутри типа название СТЕ связывается с кодом свойства КТРУ. Фильтр по размерности, запрет на расхождение квалификаторов, запрет на склейку названий, которые встречаются в одной карточке.
5. **Агрегация.** Единица счёта — уникальная модель (производитель + модель), а не карточка. На выходе точная таблица частот значений, квантили и зоны типичных значений.

Результат — файл `ste_stats.sqlite` с манифестом: хэши снимков КТРУ и СТЕ, версия кода и словарей. Ручные решения (синонимы типов, подтверждённые пары свойств) лежат в репозитории как версионируемые файлы и входят в хэш сборки.

**Онлайн-проверка** добавляет два шага после существующего уровня 1:

- **Уровень 1** работает как сейчас и не получает артефакт на вход. Единственное изменение: у статуса `unknown` появляется причина.
- **Уровень 2** по ключу (тип, свойство) достаёт статистику и отвечает, сколько моделей имеют такое значение или удовлетворяют условию. Результат относится к признаку, а не к позиции-кандидату.
- **Уровень 3** применяет детерминированные правила: заглушка, ошибка масштаба ×10ⁿ, выброс, несогласованность габаритов. Правило масштаба сверяется и с интервалами КТРУ, и с зонами СТЕ, поэтому частично работает без артефакта.

**Как защищён уровень 1.** Функция отбора кандидатов и выдачи кода не принимает артефакт и аннотации в аргументах. Автотест сравнивает множество кандидатов и итоговый код с артефактом и без него: расхождение блокирует релиз. Принятое пользователем исправление — это новый ввод, который заново проходит уровень 1 целиком.

**Без артефакта** или при несовпадении версий сервис работает как сейчас: уровень 2 отвечает «не оценивалось» с причиной, уровень 3 сохраняет правила, которым хватает КТРУ.

**Модель не обязательна.** Эмбеддинги нужны только как генератор кандидатов при составлении словарей, и только если измеренная полнота привязки окажется недостаточной. В сборке и на запросе модели нет, поэтому результат детерминирован, а потребность в VRAM равна нулю.

**Задержка.** Уровни 2 и 3 — это несколько поисков по первичному ключу на признак. Ожидаемая добавка — доли миллисекунды на признак; точное значение измеряется бенчмарком на шаге 0 плана.

## 2. Разбор подзадач

### 2.1 Привязка товаров СТЕ к типам КТРУ

Привязывать нужно к типу, а не к позиции, каскадом «лексика → подтверждение по набору свойств»; точность привязки важнее полноты.

**Тип или позиция.** Тип, по трём причинам:

- Позиции семейства различаются значениями характеристик. Привязка к позиции требует сверять значения СТЕ с интервалами КТРУ. Статистика после этого повторит интервалы КТРУ и не даст нового знания.
- Семейство до 100 позиций дробит выборку, и поддержка на позицию падает ниже любого разумного минимума.
- Тип устойчив к обновлениям КТРУ: позиции появляются и истекают чаще, чем меняется пара «наименование + ОКПД2».

Отсюда общее правило: **значения свойств в привязке не участвуют**, участвуют только наименование и названия свойств.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Лексический: головная фраза наименования против словаря типов и синонимов | Детерминирован, объясним, быстр | Синонимы и гибриды («дрель-шуруповёрт»); аксессуары («аккумулятор для шуруповёрта») | Низкая | Словарь синонимов типов |
| Через КПГЗ: товар → категория второго листа по набору свойств, категория → тип | Категорий мало, их сопоставление с типами проверяется глазами | Два перехода, ошибки перемножаются; гранулярность КПГЗ не равна КТРУ | Средняя | Таблица «категория → тип» |
| Сигнатура свойств: взвешенная доля названий свойств карточки, типичных для типа | Не зависит от наименования; отсекает рюкзаки в «одежде» | Нужен затравочный набор привязок; бедные карточки неразличимы | Средняя | Нет |
| Эмбеддинги наименований лёгкой моделью | Находит синонимы без словаря | Порог без разметки; путает близкие типы (дрель и перфоратор); причина пометки непрозрачна | Средняя, хватает CPU | Аудит кандидатов |
| Каскад из первых трёх, эмбеддинги — только кандидаты | Два независимых канала подтверждают друг друга | Сложнее в отладке; полнота ниже, чем у одной модели | Средняя | Словарь и аудит |

**Рекомендация — каскад:**

1. Нормализовать наименование: нижний регистр, лемматизация, удаление производителя и модели (они есть в отдельных полях).
2. Выделить головную фразу до первого предлога «для», «к», «под». Слова «набор», «комплект», «чехол», «запчасть» в голове помечают товар как аксессуар; он не привязывается.
3. Сопоставить головную фразу со словарём типов. Это кандидат по наименованию.
4. Построить профиль названий свойств типа на товарах из шага 3 и посчитать для каждой карточки балл сигнатуры с весами IDF.
5. Принять привязку, если оба канала согласны и отрыв от второго кандидата достаточен.
6. Остаток прогнать через эмбеддинги только как источник кандидатов, с тем же подтверждением по сигнатуре. Включать этот шаг, если измеренная полнота шагов 1–5 мала.

Кандидаты на модель для шага 6: rubert-tiny2 или multilingual-e5-small. Выбирать по точности на аудиторской выборке, а не по описанию модели.

**Порог уверенности без разметки:**

- Товары делятся на корзины по баллу сигнатуры. Из каждой корзины берётся случайная выборка на ручную проверку. Порог — нижняя корзина, где точность не ниже целевой.
- Размер выборки задаёт ширину интервала: 200 товаров на корзину дают около ±3 п.п. при точности 0,95 (95%-й биномиальный интервал).
- Контроль загрязнения: при ужесточении порога медиана и квантили ключевых свойств типа не должны заметно сдвигаться. Если сдвигаются, в выборке есть чужие товары.

**Непривязанные товары** в статистику не входят. Они остаются в отчёте сборки с причиной: нет типа в словаре, аксессуар, конфликт каналов, низкий балл. Отчёт, отсортированный по частоте головной фразы, служит очередью на пополнение словаря.

**Открытые вопросы:**

- К какому типу КТРУ относить гибриды вроде «дрель-шуруповёрт»? До решения эксперта их не привязывать.
- Нужны ли подтипы (сетевой и аккумуляторный инструмент)? Решать по данным: если распределение ключевого свойства двугорбое и расщепляется одним категориальным свойством.
- Есть ли в строке товара категория КПГЗ? Если да, подход «через КПГЗ» становится первым шагом каскада.

### 2.2 Сопоставление названий свойств СТЕ и КТРУ

Сопоставлять нужно внутри типа, с тремя жёсткими запретами и ручным подтверждением самых частых пар; автоматически принимается только то, что прошло все запреты.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Строковое сходство после нормализации (сокращения, леммы, единицы в скобках) | Просто, объяснимо | Склеивает «Ширина» и «Ширина упаковки»; не видит «Половой признак» и «Назначение» | Низкая | Словарь сокращений |
| Размерность и единица как фильтр | Детерминированный запрет: длина не сопоставляется с массой | Недостаточен: все длины совместимы между собой | Низкая | Нет |
| Пересечение значений СТЕ с допустимыми значениями КТРУ | Силён для списков: {Мужская, Женская} находит синонимичные названия | Для чисел при широких интервалах КТРУ ничего не различает; как положительный признак создаёт порочный круг | Средняя | Нет |
| Эмбеддинги названий | Синонимы без словаря | Близость «(дерево)» и «(металл)» высока, склейка вероятна | Средняя | Аудит |
| Комбинация с запретами и ручным подтверждением | Ошибка склейки блокируется до статистики | Часть пар остаётся несопоставленной | Средняя | Подтверждение частых пар |

**Три запрета, которые не дают склеить разные свойства:**

1. **Размерность.** Пара отклоняется, если размерности различаются или у одной стороны число, а у другой список.
2. **Квалификаторы.** Название разбирается на мерное слово (ширина, диаметр, масса) и набор уточнений: объект, материал, условие, экстремум. Примеры уточнений: «упаковки», «брутто», «(дерево)», «(металл)», «сиденья», «макс.», «на холостом ходу». Автоматическое сопоставление разрешено только при равных наборах уточнений с учётом словаря синонимов.
3. **Совместная встречаемость.** Если два названия СТЕ регулярно стоят в одной карточке с разными значениями, это разные свойства. «Диаметр сверления (дерево)» и «(металл)» встречаются вместе, поэтому никогда не объединяются. Синонимы приходят из разных шаблонов поставщиков и в одной карточке почти не встречаются.

**Дополнительные ограничения:**

- Несколько названий СТЕ могут вести к одному свойству КТРУ. Одно название СТЕ не может вести к двум свойствам КТРУ; такая пара уходит в ручную очередь.
- Перед объединением названий-синонимов сравниваются их распределения в логарифмической шкале. Заметное расхождение медиан отменяет объединение.
- Пересечение значений с КТРУ для чисел используется только как вето (почти нет пересечения), но не как довод «за». Для закрытых списков оно допустимо как довод «за».
- Свойства с уточнением «упаковка», «брутто», «транспортировочный» получают флаг `is_packaging` и не сопоставляются с габаритами товара.

**Статусы пары:** `auto` (прошла все запреты и совпала после нормализации), `manual` (подтверждена человеком), `rejected`, `pending`. В статистику по свойству КТРУ идут только `auto` и `manual`.

**Несопоставленные свойства СТЕ не выбрасываются.** Для них статистика считается под собственным ключом названия. Она нужна подзадаче 2.6.

**Объём ручной работы** измеряется, а не предполагается. Нужно построить кривую покрытия: пары (тип, название СТЕ), отсортированные по числу моделей, и накопленная доля сегментов. Подтверждать вручную верх кривой до согласованной доли покрытия.

**На запросе** название свойства от пользователя нормализуется тем же кодом и ищется в таблице псевдонимов точным совпадением. Эмбеддинги на запросе не нужны.

**Открытые вопросы:**

- Как сейчас извлекатель связывает название пользователя со свойством КТРУ? Таблица псевдонимов из СТЕ может расширить его словарь, но это отдельное решение.
- Кто подтверждает пары и сколько времени на это есть?

### 2.3 Очистка шума до подсчёта статистики

Шум помечается флагами, а не удаляется; главный приём — считать по уникальным моделям и брать согласованное значение модели.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Правила-фильтры с флагами | Каждое исключение имеет причину; доли флагов сами становятся метрикой качества | Не ловят ошибки, похожие на обычные числа | Низкая | Списки заглушек и уточнений |
| Робастные оценки без фильтрации (медиана, квантили) | Не требуют решений по каждому сегменту | Заглушки-нули при большой доле сдвигают даже квантили | Низкая | Нет |
| Согласование по модели: одна модель — одно значение | Исправляет единичные ошибки вроде 1212 мм; убирает перевес популярных моделей | Зависит от заполненности полей «модель» и «производитель» | Средняя | Нет |
| Детектор аномалий на ML (isolation forest и подобные) | Находит неочевидные сочетания | Причину пометки нельзя показать; пороги без разметки не настроить | Средняя | Аудит |
| Комбинация первых трёх | Каждый слой закрывает слабость другого | Больше кода и тестов | Средняя | Списки |

**Рекомендация — комбинация первых трёх.** Правила по видам шума:

| Шум | Правило | Что происходит со значением |
| --- | --- | --- |
| «(не задано)», «-», пусто | Точное совпадение со списком заглушек | Исключается; доля заглушек хранится |
| Ноль у положительной физической величины (масса, длина, мощность, момент, ёмкость, время) | Размерность + значение 0 | Исключается как заглушка |
| Ноль у счётного свойства без размерности | Не решается автоматически | Сохраняется; доля нулей хранится отдельно |
| Значения-маркеры (например, 999) | Значение аномально частое сразу во многих несвязанных свойствах | Кандидат в список заглушек после ручной проверки |
| Повтор свойства с тем же значением | Дедупликация внутри карточки | Одно значение |
| Повтор свойства с разными значениями | Флаг `multi_value` | В точечную статистику не входит; доля хранится |
| Перечисление через запятую | Для списков — разбить на множество; для чисел — `multi_value` | По виду свойства |
| Единица в названии: «Крутящий момент (Нм)» | Единица берётся из названия | Канонизируется |
| Число без единицы | Принять доминирующую единицу свойства, только если она преобладает и распределения совпадают | Флаг `unit_inferred`; иначе исключается |
| Составные габариты «38.5x20x22» | Разбор в тройку чисел | Без единицы — `unit_missing`, в статистику не идёт |
| Габариты и вес упаковки | Уточнение в названии → `is_packaging` | Отдельное свойство, с товаром не смешивается |
| Грубая ошибка числа (1212 мм вместо 12) | Согласование по модели, затем ручной список физических границ | Исключается или остаётся как редкое значение |

**Согласование по модели.** Ключ — нормализованные производитель и модель. Если у модели несколько карточек, берётся значение большинства. Без большинства модель не участвует в статистике этого свойства. При пустой модели карточка считается отдельной единицей.

**«Эхо»-группы.** Небольшая группа значений ровно в 10, 100 или 1000 раз дальше основной — след ошибок единиц в самих выгрузках. Она получает флаг `echo`, в типичную зону не входит, но сохраняется для отчёта.

**Повтор с разными значениями** — это либо ошибка, либо диапазон. В первой версии такие значения исключаются. Если у свойства доля `multi_value` велика, оно уходит на ручной разбор: вероятно, поставщики так записывают минимум и максимум.

**Отчёт сборки** показывает долю каждого флага по направлению и по типу. Резкий рост доли между снимками — сигнал об изменении формата выгрузки.

**Открытые вопросы:**

- Насколько заполнены «модель» и «производитель»? Измерить долю пустых до реализации согласования.
- «0.00000» — это ноль поставщика или пустое поле, заполненное при выгрузке? От ответа зависит трактовка нулей у счётных свойств.

### 2.4 Статистика по свойству типа

Хранить нужно точную таблицу частот значений по моделям, квантили и «зоны»; уровень 2 отвечает числом моделей, которые удовлетворяют условию пользователя.

**Числовые свойства**

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Среднее ± 3σ | Просто | Не робастно; для скошенных величин границы бессмысленны | Низкая | Нет |
| Квантили p1–p99 | Объяснимо: «у 90% моделей…» | Один интервал скрывает многогорбость | Низкая | Нет |
| Медиана и MAD в логарифмической шкале | Робастный балл удалённости | Плохо переводится в текст для пользователя; не годится для дискретных рядов | Низкая | Нет |
| Смесь распределений или KDE | Описывает многогорбость | Неустойчиво на малых выборках; параметры нельзя показать | Средняя | Нет |
| Точная таблица частот + зоны по разрывам | Точный ответ «у N из M»; многогорбость видна как несколько зон; Decimal без округления | Больше строк в артефакте | Низкая | Нет |

**Рекомендация — таблица частот и зоны, квантили как текст для сообщений:**

- **Таблица частот.** Для пары (тип, свойство) хранится каноническое значение, число моделей, число карточек и накопленное число моделей. Любой оператор (=, ≥, ≤, диапазон, «не») сводится к вопросу «сколько моделей удовлетворяют условию».
- **Квантили** p1, p5, p25, p50, p75, p95, p99 и очищенные минимум и максимум — готовые числа для формулировок.
- **Шкала.** Логарифмическая, если все значения положительны и отношение p95/p5 выше порога; иначе линейная. Порог подбирается на оценке (2.8).
- **Зоны.** Значения раскладываются по фиксированным интервалам шкалы. Соседние занятые интервалы сливаются в зону; зона с малой поддержкой отбрасывается. Несколько зон означают многогорбость: «10,8–12 В и 18–20 В».
- **Дискретные числа** (напряжения, размеры одежды): при малом числе различных значений зоны не строятся, сообщение перечисляет самые частые значения.

**Статусы уровня 2:**

| Статус | Условие | Что показывается |
| --- | --- | --- |
| `typical` | Значение в зоне; условию удовлетворяет заметная доля моделей | По умолчанию ничего |
| `rare` | Вне зон, но внутри наблюдаемого диапазона; или доля удовлетворяющих мала | Пометка в деталях |
| `unseen` | Вне наблюдаемого диапазона; условию не удовлетворяет ни одна модель | Пометка с числами и кратностью до ближайшей границы |
| `not_assessed` | Нет артефакта, тип не привязан, мало данных, свойство не сопоставлено, открытый словарь | Причина |

**Текстовые свойства**

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Частоты после нормализации (регистр, ё, пробелы, пунктуация, леммы) | Детерминированно; «мужская» и «мужской» сливаются | Не видит настоящих синонимов | Низкая | Нет |
| Кластеры по редакционному расстоянию | Собирает опечатки | Склеивает короткие разные значения: «S» и «M», «44» и «46» | Низкая | Аудит кластеров |
| Словарь соответствия значениям КТРУ | Значение СТЕ получает код значения КТРУ | Только для сопоставленных свойств | Средняя | Подтверждение частых значений |
| Эмбеддинги значений | Синонимы без словаря | Непрозрачно; антонимы близки в пространстве | Средняя | Аудит |

Рекомендация: нормализация с леммами плюс словарь соответствия КТРУ для частых значений. Близкие написания не объединяются, а показываются как подсказка «ближайшие по написанию».

**Открытый словарь.** Если отношение числа различных значений к числу моделей высоко (артикул, название коллекции, свободный текст), свойство получает вид `open_vocab`. О таких свойствах уровень 2 не говорит «не встречается».

**Минимальная поддержка**

- Считать по моделям и производителям. Один производитель не должен задавать «типичность» типа.
- Три ступени: ниже N1 уровень 2 молчит; от N1 до N2 даёт только утверждения «встречается у…»; выше N2 — полный набор, включая «не встречается».
- N2 привязывается к силе утверждения по правилу трёх. Если значения нет ни у одной из n моделей, верхняя 95%-я граница его доли примерно 3/n. «Реже 5%» требует n ≥ 60, «реже 1%» — n ≥ 300.
- N1 калибруется: из крупных типов берутся подвыборки разного размера, измеряется разброс границ зон и доля ложных тревог на отложенных моделях. N1 — наименьший размер, при котором доля не выше целевой.
- Стартовые значения для первого прогона: N1 = 30 моделей и 3 производителя, N2 = 60 моделей и 5 производителей. Это предположение до калибровки, а не измерение.

**Открытые вопросы:**

- Показывать пользователю число моделей или карточек? Рекомендую модели; карточки хранить для отладки.
- Как трактовать значения-диапазоны в СТЕ («0–1500 об/мин»)? В первой версии такие свойства не оцениваются.

### 2.5 Правила уровня 3

Уровень 3 — четыре детерминированных правила; исправление предлагается только при единственном объяснении, а правило масштаба сверяется и с КТРУ, и с СТЕ.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Ручной список физических границ (как сейчас) | Работает без данных | Покрывает мало свойств и не растёт сам | Низкая | Высокая на каждое свойство |
| Проверка преобразования: значение × k попадает в эталонный диапазон | Даёт и пометку, и исправление; причина очевидна | Молчит, когда типичный диапазон шире множителя; могут подойти несколько k | Низкая | Нет |
| Робастный балл удалённости в логарифмической шкале | Ловит ошибки без «красивого» множителя | Нет исправления; порог без разметки подбирается только синтетикой | Низкая | Нет |
| Парные ограничения между свойствами (A ≤ B) | Ловит перестановки и внутренние противоречия | Ограничения нужно подтверждать | Средняя | Подтверждение пар |
| Оценка правдоподобия моделью (ML или LLM) | Не требует правил | Недетерминированно; причину и данные показать нельзя | Высокая | Аудит |

**Рекомендация — первые четыре слоями.** Граница с уровнем 2: уровень 2 сообщает факт частоты, уровень 3 срабатывает только при признаке ошибки.

| Правило | Условие срабатывания | Нужен ли артефакт | Предложение |
| --- | --- | --- | --- |
| `placeholder` | Значение 0, «не задано», «-» у положительной физической величины или значение из списка маркеров | Нет | Уточнить значение или убрать характеристику |
| `scale` | Значение не подходит ни одной позиции по КТРУ или имеет статус `unseen`/`rare`; при этом ровно один множитель k делает его допустимым по КТРУ или типичным по СТЕ | Частично: при узких интервалах КТРУ хватает уровня 1 | Та же цифра в другой единице либо число без лишнего нуля |
| `outlier` | Статус `unseen`, удалённость от границы диапазона выше порога кратности, `scale` объяснения не нашёл; либо нарушена граница из ручного списка | Да, кроме ручного списка | Нет; просьба подтвердить значение |
| `dimensions` | Габариты нетипичны для своих осей, но ровно одна перестановка делает все типичными; либо нарушено подтверждённое парное ограничение | Да | Перестановка осей или указание на конфликтующую пару |

**Набор множителей** выводится из лестницы единиц размерности свойства:

- длина: 10, 100, 1000 и обратные (мм, см, м);
- масса, мощность, объём, ёмкость: 1000 и обратный (г/кг, Вт/кВт, мл/л, мА·ч/А·ч);
- любая размерность: 10 и 1/10 (лишний или пропущенный ноль, потерянная запятая).

Дюймы добавлять, только если профилирование СТЕ и журналов запросов покажет дюймовые значения.

**Защита `scale` от ложных срабатываний:**

- Исходное значение вне зон при поддержке не ниже N2 либо недопустимо по КТРУ для всех кандидатов.
- Преобразованное значение лежит между p5 и p95 зоны, а не на её краю.
- Множитель единственный. Если подходят несколько, выдаётся предупреждение с перечнем вариантов без готового исправления.

Если типичный диапазон свойства шире множителя, правило молчит по построению. Это честный предел метода; он измеряется в 2.8 как «потолок обнаружимости».

**Как формулировать исправление:**

- Единица не указана. Это не предупреждение, а уточняющий вопрос «в каких единицах?» с вариантами по убыванию правдоподобия.
- Единица указана, множитель совпадает с шагом лестницы. Предлагается та же цифра с другой единицей: «75 см вместо 75 мм». Цифры пользователя не меняются.
- Множитель 10 без подходящей единицы. Формулировка «возможно, лишний ноль: 140 вместо 1400».

Шаблон сообщения: что заметили → на чём основано, с числами → что предлагаем → две кнопки «Заменить» и «Оставить». Слова «ошибка» в тексте нет, только «возможно».

**Объект предложения:** `rule`, `feature_ids`, `original {value, unit}`, `proposed {value, unit}`, `evidence {source: ktru | ste, n_models, zone, k}`, `actions: [accept, keep]`. При `accept` клиент повторяет запрос с новым значением и идентификатором предложения. При `keep` предупреждение в этой сессии больше не показывается.

**Парные ограничения** добываются из СТЕ как кандидаты: пары свойств одной размерности, где A ≤ B выполняется почти у всех моделей с обоими свойствами. В таблицу ограничений пара попадает только после ручного подтверждения. Примеры: высота сиденья ≤ общая высота, масса нетто ≤ масса брутто.

**Открытые вопросы:**

- Предлагать ли исправление, когда значение допустимо по КТРУ, но нетипично по СТЕ? Рекомендую да, с более низким приоритетом показа.
- Можно ли журналировать принятые и отклонённые предложения? Доля принятия по правилам — главная метрика качества в эксплуатации.

### 2.6 Свойства, которых нет в КТРУ

Вердикт о свойстве складывается из трёх источников: семейство КТРУ, распространённость в СТЕ для типа и встречаемость в других типах. «Бессмыслица» формулируется как «не встречается у N моделей», а не как утверждение.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Распространённость в СТЕ: доля моделей типа, у которых свойство указано | Прямой ответ с числами | Зависит от привязки; редкое реальное свойство выглядит отсутствующим | Низкая | Нет |
| Второй лист (КПГЗ): свойство числится типовым для категории | Курируемый источник; работает при малой поддержке | Нужна таблица «категория → тип»; это не КТРУ | Средняя | Таблица категорий |
| Контраст между типами: свойство частое в других типах и отсутствует в этом | Отличает «чужое» свойство от «неизвестного»; даёт подсказку, откуда оно | Омонимы вроде «Размер» | Низкая | Нет |
| Смысловая близость по эмбеддингам или LLM | Не требует данных о типе | «Так бывает» без чисел; причину не показать | Средняя и выше | Аудит |

**Рекомендация — первые три.** Проверка идёт по порядку, первое совпадение задаёт вердикт:

1. Название совпало с псевдонимом свойства КТРУ этой позиции → `synonym`. Свойство передаётся на уровень 1 только после подтверждения пользователем.
2. Свойство есть у других позиций семейства → `in_family`. Это знание из КТРУ, артефакт не нужен.
3. Свойство указано у достаточной доли моделей типа либо числится в КПГЗ для сопоставленной категории → `known_for_type`.
4. Свойство встречается в других типах, а в этом его нет ни у одной модели при поддержке не ниже N2 → `known_elsewhere`.
5. Свойство не найдено нигде → `unknown`.
6. Тип не привязан или данных мало → `not_assessed`.

**Что показывать с учётом флага «можно добавлять характеристики»:**

| Вердикт | Добавлять можно | Добавлять нельзя |
| --- | --- | --- |
| `synonym` | «Возможно, это характеристика КТРУ „…“. Использовать её?» | То же |
| `in_family` | «В этой позиции такой характеристики нет, но она есть у соседних позиций» | То же |
| `known_for_type` | «На выбор кода не влияет. Свойство обычное для таких товаров (у N из M моделей). Его можно указать дополнительно» | «На выбор кода не влияет. Свойство обычное для таких товаров, но для этой позиции дополнительные характеристики не добавляются» |
| `known_elsewhere` | «У таких товаров свойство не встречается (0 из M моделей). Встречается у: … Проверьте, к тому ли товару оно относится» | То же |
| `unknown` | «Свойство не найдено ни в КТРУ, ни в выгрузках. Проверьте название» | То же |
| `not_assessed` | «В позиции КТРУ такой характеристики нет. Проверить по выгрузкам не удалось» | То же |

Для `known_for_type` значение дополнительно проходит уровни 2 и 3 по статистике свойства СТЕ.

**Порог распространённости** подбирается по данным. Нужно построить распределение доли моделей по свойствам внутри крупных типов. Обычно оно двугорбое: свойства шаблона и случайные поля. Порог ставится в провале и проверяется ручным просмотром свойств рядом с ним. Дополнительное условие — несколько производителей, чтобы поле одного поставщика не стало «реальным свойством».

**Подсказка о неверном типе.** Если несколько свойств запроса получили `known_elsewhere` и указывают на один и тот же другой тип, показывается одна общая подсказка. Тип система при этом не меняет.

**Открытые вопросы:**

- Формулировки про добавление характеристик нужно согласовать с экспертом по закупкам: у них есть правовые последствия.
- Считать ли роль «базовая» из КПГЗ достаточной для `known_for_type` без поддержки в карточках?

### 2.7 Встраивание в ответ и интерфейс

В ответе нужны три независимые оси: статус по КТРУ с причиной `unknown`, эмпирический статус признака и список предупреждений. На один признак показывается не больше одного сообщения.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Расширить единый статус: `valid`, `invalid`, `unknown_missing`, `atypical`, `suspect` | Одно поле, просто клиенту | Смешивает уровни; `atypical` со временем начнут читать как `invalid` | Низкая | Нет |
| Независимые поля по уровням у каждого признака | Уровни нельзя перепутать; уровень 1 не меняется | Приоритет показа нужно где-то вычислять | Низкая | Нет |
| Плоский список замечаний со ссылками на признаки | Удобен для панели замечаний | Состояние признака приходится собирать из списка | Низкая | Нет |
| Поля по уровням + список предупреждений, приоритет считает сервер | Клиент только отображает; правила показа в одном месте | Ответ становится больше | Низкая | Нет |

**Рекомендация — последний вариант.** Поля:

| Поле | К чему относится | Значения | Назначение |
| --- | --- | --- | --- |
| `ktru.status` | Признак × кандидат | `valid`, `invalid`, `unknown` | Как сейчас, без изменений |
| `ktru.unknown_reason` | Признак × кандидат | `not_specified`, `property_absent`, `not_comparable` | Разводит «не указано» и «не проверено» |
| `empirical.status` | Признак | `typical`, `rare`, `unseen`, `not_assessed` | Уровень 2 |
| `empirical.not_assessed_reason` | Признак | `no_artifact`, `type_unbound`, `low_support`, `property_unmapped`, `open_vocab` | Почему уровень 2 молчит |
| `empirical.evidence` | Признак | Число моделей и производителей, число удовлетворяющих условию, зоны, частые значения, тип, версия артефакта | Числа для сообщения |
| `presence.verdict` | Признак вне КТРУ | Вердикты из 2.6 | Реальное свойство или нет |
| `warnings[]` | Ответ | Правило, важность, признаки, текст, основание, предложение | Уровень 3 |
| `display.primary` | Признак | Идентификатор главного сообщения и его важность | Сервер выбрал, что показать |
| `meta.levels` | Ответ | Состояние уровней 2 и 3, снимок КТРУ, версия артефакта | Деградация видна клиенту |

Уровень 2 относится к признаку, а не к паре «признак × кандидат». Так его физически нельзя использовать для отбора позиций.

**Четыре состояния в интерфейсе:**

| Состояние | Источник | Как выглядит |
| --- | --- | --- |
| Не указано | `unknown_reason = not_specified` | Нейтральная строка в блоке «Можно уточнить»; это повод для вопроса, а не замечание |
| Не проверено по КТРУ | `property_absent`, `not_comparable` | Серая метка «не проверено» с причиной |
| Нетипично по выгрузкам | `empirical.status = unseen` | Информационная метка с числами и припиской «по КТРУ допустимо», если это так |
| Вероятная ошибка | `warnings[]` с предложением | Выделенная карточка с кнопками «Заменить» и «Оставить» |

**Как не перегрузить пользователя:**

- Типичное значение не порождает сообщений. Числа доступны по клику на признак.
- Одно сообщение на признак. Приоритет: несовместимо по КТРУ → вероятная ошибка → не встречается → редкое.
- Если уровень 3 объясняет отказ уровня 1, сообщения объединяются: «не подходит по КТРУ; возможно, имелись в виду сантиметры».
- Статус `rare` по умолчанию скрыт в деталях; на экран выходит только `unseen`.
- Видны первые три замечания, остальные свёрнуты под «ещё N».
- Отклонённое предупреждение в сессии не возвращается.
- По каждому правилу считается доля принятых и отклонённых предложений. Правило с низкой долей принятия понижает в приоритете команда, а не система.

**Открытые вопросы:**

- Одинаков ли интерфейс для закупщика и поставщика? Поставщику эмпирические пометки полезнее.
- Есть ли внешние потребители API? Новые поля добавляются без изменения значений `ktru.status`, но это стоит подтвердить.

### 2.8 Оценка без эталона

Оценка состоит из трёх независимых частей: синтетика с разбиением по производителям, доля тревог на реальных описаниях и малый ручной аудит. Ни одна не заменяет другую.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Синтетические ошибки в отложенных строках СТЕ | «Разметка» в любом объёме; точные полнота и точность исправления | Распределение ошибок придумано; отложенные строки сами шумные | Низкая | Нет |
| Доля тревог на реальных чистых описаниях | Измеряет то, что увидит пользователь | Нужен источник описаний; «чистоту» приходится проверять | Средняя | Просмотр тревог |
| Ручной аудит выборок | Единственный источник истины о привязке и сопоставлении | Дорого; малые выборки дают широкие интервалы | Высокая | Основная |
| Согласованность с КТРУ: доля зон СТЕ внутри допустимых интервалов КТРУ | Бесплатно; ловит грубые ошибки привязки и единиц | Не доказательство: интервалы КТРУ широкие | Низкая | Нет |

**Рекомендация — все четыре; согласованность с КТРУ только как дымовой тест сборки.**

**Протокол синтетики:**

1. Разбить модели на пять блоков по производителю. Статистика строится на четырёх блоках, тест идёт на пятом, и так по кругу.
2. Из тестового блока взять значения, которые прошли очистку и типичны по статистике остальных блоков. Иначе неясно, что считать чистым.
3. Внести в карточку одну ошибку: ×10, ÷10, ×1000, ÷1000, чужая единица той же размерности, единица другой размерности, заглушка, перестановка габаритов.
4. Прогнать на двух уровнях. Структурный: пары «свойство — значение» подаются прямо в проверку. Текстовый: карточка превращается в описание и проходит извлечение.
5. По каждому виду ошибки посчитать полноту пометки, точность предложенного исправления и долю пометок на неиспорченных полях той же карточки.

**Потолок обнаружимости.** Часть ошибок не видна в принципе: ×10 у свойства с широким диапазоном остаётся типичным. Для каждого вида ошибки считается доля внесений, которые выводят значение из зон. Полнота сообщается и абсолютная, и относительно этого потолка.

**Как избежать утечки:**

| Разбиение | Что протекает | Применение |
| --- | --- | --- |
| По карточкам | Одна модель у разных поставщиков попадает в обе части | Не использовать |
| По моделям | Соседние модели линейки почти идентичны | Вспомогательная оценка |
| По производителям | Почти ничего; оценка пессимистична для типов с малым числом брендов | Основная оценка |

- Сообщать обе оценки. Разрыв между ними показывает, насколько система запоминает линейки вместо типа.
- Пороги (N1, N2, кратность выброса, выбор шкалы) подбираются только на обучающих блоках. Итоговые метрики считаются на блоке, который в подборе не участвовал.
- Дубликаты карточек между файлами направлений удаляются до разбиения.
- При пустом производителе группировка идёт по нормализованному наименованию.
- Рабочий артефакт после оценки строится на всех данных.

**Ложные тревоги на реальных описаниях.** Источники по убыванию ценности: журнал запросов сервиса, описания от экспертов по закупкам, существующий регрессионный набор. Каждая тревога просматривается вручную и получает метку «находка» или «ложная». Отложенные строки СТЕ без внесённых ошибок дают только верхнюю оценку: в них есть собственный шум.

**Ручной аудит:**

| Объект | Выборка | Метрика |
| --- | --- | --- |
| Привязка «товар → тип» | По 200 товаров на корзину балла | Точность по корзинам |
| Пары свойств со статусом `auto` | Случайная выборка плюс верх кривой покрытия | Точность |
| Тревоги на чистых описаниях | Все, если их мало; иначе случайные 200 | Доля ложных |
| Кандидаты в парные ограничения | Все | Подтверждено или нет |

Часть выборки размечают два человека независимо; доля совпадений показывает, насколько сама задача аудита однозначна.

**Открытые вопросы:**

- Есть ли журнал реальных запросов и можно ли его использовать для оценки?
- Сколько часов экспертов доступно на аудит? От этого зависят размеры выборок и ширина интервалов.

### 2.9 Версионирование и воспроизводимость

Артефакт собирается целиком и детерминированно, несёт манифест с хэшами входов, а при запуске сверяется со снимком КТРУ по каждому типу отдельно.

| Подход | Плюсы | Минусы и риски | Стоимость | Ручная работа |
| --- | --- | --- | --- | --- |
| Полная пересборка с манифестом | Просто; одно состояние, которое легко воспроизвести | Каждый раз пересчитывается всё | Низкая | Нет |
| Инкрементальная сборка по типам | Быстро при малых изменениях | Сложная инвалидация: согласование по моделям и контраст между типами глобальны | Высокая | Нет |
| Кэш стадий по хэшу входа | Ускоряет повтор после правки словаря | Больше инфраструктуры | Средняя | Нет |
| Файл без версии рядом с сервисом | Ничего не нужно делать | Молчаливое расхождение с КТРУ; сообщение нельзя воспроизвести | Нулевая | Нет |

**Рекомендация — полная пересборка.** Кэш стадий добавлять, только если измеренное время сборки мешает работе со словарями.

**Манифест:**

| Поле | Содержание |
| --- | --- |
| `schema_version` | Версия схемы артефакта |
| `ktru_snapshot_id` | SHA-256 нормализованного снимка КТРУ и его дата |
| `ste_snapshot_ids` | SHA-256 каждого из трёх файлов выгрузки |
| `pipeline_commit` | Коммит кода сборки |
| `dictionaries_hash` | Хэш словарей: синонимы типов, уточнения, заглушки, подтверждённые пары, ограничения |
| `config_hash` | Хэш порогов и параметров |
| `content_hash` | Хэш логического дампа таблиц в фиксированном порядке |
| `built_at`, `row_counts`, `quality_report` | Справочные поля; в `content_hash` не входят |

**Детерминированность сборки:**

- Фиксированный порядок сортировки во всех агрегациях и фиксированный контекст Decimal.
- В сборке нет случайных выборок и нет модели. Предложения модели проходят ручное подтверждение и попадают в словари.
- Проверка в CI: две сборки из одинаковых входов дают одинаковый `content_hash`.

**Проверка при запуске:**

1. Файла нет, он не читается или `schema_version` не поддерживается. Уровень 2 выключается, уровень 3 работает только по КТРУ, сервис стартует.
2. `ktru_snapshot_id` совпадает с загруженным КТРУ. Всё включено.
3. Снимок не совпадает. Сверка идёт по типам: у каждого типа хранится отпечаток кодов свойств, их единиц и видов. Тип с совпавшим отпечатком работает; остальные получают `not_assessed` с причиной `stale_type`.
4. Доля устаревших типов выше порога. Эксплуатация получает сигнал о пересборке.

Каждый исход пишется в журнал и в метрику. Ни один из них не мешает уровню 1.

**Замена и откат.** Новый файл проверяется и подключается атомарно; предыдущий хранится для отката. Версия артефакта возвращается в каждом ответе, поэтому любое сообщение пользователю можно воспроизвести.

**Отчёт о различиях между сборками.** Для каждой пары (тип, свойство) сравниваются медиана и границы зон. Сдвиги сверх допуска выносятся в список на просмотр до выпуска.

**Открытые вопросы:**

- Как часто обновляются КТРУ и выгрузки СТЕ? От этого зависит, нужна ли автоматическая пересборка.
- Есть ли у карточек СТЕ даты? Без них нельзя учесть устаревание товаров.

## 3. Схема производного артефакта

Артефакт — один файл SQLite только для чтения. Ожидаемый размер — десятки мегабайт, верхняя граница — около 0,2 ГБ; обе оценки зависят от допущений ниже и проверяются одним запросом.

| Таблица | Ключ | Основные поля | Назначение |
| --- | --- | --- | --- |
| `manifest` | `key` | `value` | Версии и хэши (2.9) |
| `types` | `type_id` | `type_key`, `ktru_name`, `okpd2`, `fingerprint`, `n_models`, `n_manufacturers`, `n_cards` | Типы КТРУ и их поддержка |
| `props` | `prop_id` | `type_id`, `source` (ktru или ste), `ktru_prop_code`, `ste_key`, `display_name`, `kind`, `dimension`, `canon_unit`, `scale_exp`, `is_packaging`, `n_models`, `n_manufacturers`, `prevalence`, `placeholder_share`, `multi_value_share`, квантили `p01…p99`, `min_clean`, `max_clean` | Сводка по свойству типа |
| `prop_alias` | `type_id`, `alias_norm` | `prop_id`, `origin`, `status` | Поиск свойства по названию на запросе |
| `value_freq` | `prop_id`, `value_sort` | `value_dec`, `n_models`, `n_cards`, `cum_models` | Точные частоты числовых значений |
| `zones` | `prop_id`, `zone_no` | `lo`, `hi`, `n_models`, `is_echo` | Зоны типичных значений |
| `text_freq` | `prop_id`, `value_norm` | `display`, `n_models`, `n_cards`, `ktru_value` | Частоты текстовых значений |
| `pair_constraints` | `type_id`, `prop_a`, `prop_b` | `relation`, `support`, `holds_share`, `confirmed_by` | Подтверждённые ограничения A ≤ B |
| `kpgz_props`, `kpgz_type_map` | `kpgz_code`, `prop_key` | `role`, `kind`, `unit`, `type_id` | Типовые характеристики второго листа |
| `prop_global` | `prop_key_norm` | Типы с наибольшей распространённостью свойства | Контраст между типами (2.6) |
| `examples` | `prop_id`, `kind` | `manufacturer`, `model`, `value_dec` | Несколько моделей на границах диапазона для показа основания |

**Decimal без округления.** `value_dec` хранит каноническую запись Decimal как текст. `value_sort` — целое, равное значению в канонической единице, умноженному на 10 в степени `scale_exp`. Степень выбирается при сборке так, чтобы все значения свойства были целыми. Если значение не помещается в 64 бита, сборка завершается ошибкой, а не округляет.

Пример запроса уровня 2 для условия «значение ≥ v»:

```sql
SELECT COALESCE(SUM(n_models), 0) AS n_matching
FROM value_freq
WHERE prop_id = :prop_id AND value_sort >= :v_sort;
```

Поле `cum_models` позволяет заменить суммирование одним поиском по ключу, если диапазонный запрос окажется заметным в профиле.

**Оценка размера.** Известно одно число: 3,6 млн сегментов. Остальное — допущения:

- a — доля сегментов, прошедших очистку и привязку;
- c — отношение числа различных троек (тип, свойство, значение) к числу сегментов;
- b — байт на строку таблицы частот вместе с индексом; принято 60.

| Сценарий | Допущение | Строк в таблицах частот | Размер |
| --- | --- | --- | --- |
| Верхняя граница | a = 1, c = 1: ни одного повтора значений | 3,6 млн | Около 0,2 ГБ |
| Ожидаемый | a × c от 5 до 15% | 180–540 тыс. | Около 11–32 МБ |

Остальные таблицы растут с числом пар (тип, свойство), а не с числом сегментов, и на порядок меньше. Даже верхняя граница примерно в 9 раз меньше исходной базы в 1,9 ГБ.

**Как измерить c до сборки** (имена столбцов условные; категория файла заменяет тип и даёт оценку снизу):

```sql
SELECT COUNT(*) AS segments,
       COUNT(DISTINCT file_category || '|' || name_key || '|' || value_canon) AS triples
FROM segments
WHERE is_placeholder = 0;
```

**Если размер окажется велик.** Для свойств с очень большим числом различных значений точная таблица заменяется гистограммой с фиксированными интервалами. Такое свойство получает флаг `approx`, а сообщения по нему формулируются диапазонами, без «у 0 моделей».

**Доступ на запросе.** `props` и `prop_alias` загружаются в память при запуске. `value_freq` и `text_freq` читаются из файла по первичному ключу в режиме только для чтения. Если бенчмарк покажет заметную задержку, таблицы частот тоже переносятся в память как отсортированные массивы.

## 4. Примеры сообщений пользователю

Каждое сообщение называет наблюдение, основание с числами и, если есть, действие. Числа в примерах условные, кроме диапазона 8–140 Н·м из постановки задачи.

| Ситуация | Статусы | Текст | Действия |
| --- | --- | --- | --- |
| Типичное значение | `ktru: valid`, `empirical: typical` | По умолчанию сообщения нет. По клику на признак: «Крутящий момент 45 Н·м — обычное значение. У 412 моделей шуруповёртов встречается от 8 до 140 Н·м». | Нет |
| Нетипичное значение | `ktru: valid`, `empirical: unseen` | «Напряжение аккумулятора 16 В по КТРУ допустимо, но не встречается ни у одной из 380 моделей шуруповёртов. Самые частые значения: 12, 14,4 и 18 В». | «Понятно» |
| Вероятная ошибка единицы | `ktru: invalid` для всех кандидатов, `warning: scale` | «Высота 75 мм не подходит ни одной позиции КТРУ „Стол письменный“. У 1 240 моделей высота — от 700 до 780 мм. Возможно, вы имели в виду 75 см?» | «Заменить на 75 см», «Оставить 75 мм» |
| Свойство не из КТРУ, но реальное | `presence: known_for_type` | «Характеристики „Наличие подсветки“ в этой позиции КТРУ нет, на выбор кода она не влияет. Для шуруповёртов это обычное свойство: указано у 212 из 412 моделей. Его можно указать дополнительно». | Нет |
| Свойство-бессмыслица | `presence: known_elsewhere` | «„Крутящий момент“ не встречается ни в КТРУ для стульев, ни у одной из 3 150 моделей стульев в выгрузках. Свойство встречается у шуруповёртов и гайковёртов. Проверьте, к тому ли товару оно относится». | «Убрать характеристику», «Оставить» |

В четвёртом примере последняя фраза зависит от флага позиции. Если добавлять характеристики нельзя, она заменяется на «Для этой позиции дополнительные характеристики не добавляются».

В третьем примере основание двойное: отказ по КТРУ и зона по СТЕ. Без артефакта остаётся первая часть, и предложение всё равно выдаётся, потому что 750 мм допустимо по КТРУ.

## 5. План оценки

Три порога жёсткие: неизменность уровня 1, воспроизводимость сборки и задержка. Остальные пороги — предложения, которые фиксируются после первого замера базовой линии.

| Метрика | Как считается | Данные | Порог приёмки |
| --- | --- | --- | --- |
| Неизменность уровня 1 | Доля запросов, где кандидаты, статусы и код совпадают с артефактом и без него | Регрессионный набор и отложенные карточки как запросы | 100%, жёсткий |
| Воспроизводимость сборки | Равенство `content_hash` двух сборок из одних входов | CI | 100%, жёсткий |
| Задержка | Прирост p50 и p95 к текущим значениям | Бенчмарк на регрессионном наборе | p50 не более +2 мс, p95 не более +5 мс; согласовать |
| Точность привязки | Доля верных привязок в аудите принятой корзины | 200 товаров на корзину | Не ниже 0,95; нижняя граница интервала не ниже 0,92 |
| Покрытие привязки | Доля товаров с привязкой и доля типов с поддержкой не ниже N1 | Отчёт сборки | Без порога; базовая линия |
| Точность пар свойств `auto` | Доля верных пар в аудите | Случайная выборка пар | Не ниже 0,98 |
| Заглушки: полнота | Доля внесённых заглушек с пометкой | Синтетика | Не ниже 0,99 |
| Ошибка ×1000 и ÷1000: полнота к потолку | Доля помеченных среди обнаружимых | Синтетика, разбиение по производителям | Не ниже 0,90 |
| Ошибка ×10 и ÷10: полнота к потолку | То же | То же | Не ниже 0,70 |
| Точность исправления | Доля предложений, совпавших с исходным значением | Синтетика | Не ниже 0,90 |
| Перестановка габаритов: полнота к потолку | Доля помеченных среди обнаружимых | Синтетика | После базовой линии |
| Ложные тревоги уровня 3 | Доля признаков реальных описаний с предупреждением, признанным ложным | Журнал запросов или экспертный набор, ручной просмотр | Не выше 2% признаков |
| `unseen` на реальных описаниях | Доля признаков со статусом `unseen` | То же | Не выше 5% признаков |
| Разрыв между разбиениями | Разница полноты по моделям и по производителям | Синтетика | Без порога; больше 10 п.п. — разбор |
| Доля принятых предложений | Принято к сумме принятых и отклонённых, по правилам | Телеметрия после запуска | Наблюдение, не приёмка |

**Откуда данные:**

- **Синтетика** — отложенные блоки СТЕ по протоколу из 2.8. Объём не ограничен.
- **Реальные описания** — журнал запросов сервиса. Если журнала нет, эксперты пишут набор описаний, поровну по трём направлениям.
- **Аудит** — выборки из отчёта сборки. Разметка в таблице с двумя столбцами: «верно или нет» и комментарий.

**Порядок.** Сначала все метрики тревог снимаются на текущей системе: уровень 1 и ручной список границ. Это базовая линия. Каждый следующий шаг плана сравнивается с ней, а не с нулём.

**Чего эта оценка не покажет.** Синтетика не знает, какие ошибки люди делают на самом деле и как часто. Ответ на это даёт только телеметрия принятых и отклонённых предложений после запуска.

## 6. Пошаговый план реализации

Первые три шага закрывают проблему 4 и часть проблемы 3 вообще без выгрузок СТЕ; артефакт появляется на шаге 6 и сначала работает на нескольких пилотных типах.

| № | Шаг | Что даёт | Критерий готовности |
| --- | --- | --- | --- |
| 0 | Страховочная сетка: регрессионный набор запросов, снимок ответов уровня 1, бенчмарк задержки | Базовая линия для всех следующих шагов | Тест неизменности и бенчмарк запускаются в CI |
| 1 | Поле `unknown_reason` и два разных состояния в интерфейсе | Решена проблема 4 | Значения `ktru.status` на регрессионном наборе не изменились; в интерфейсе «не указано» и «не проверено» выглядят по-разному |
| 2 | Правило `placeholder` и правило `scale` по интервалам КТРУ; объект предложения и кнопки «Заменить», «Оставить» | Часть проблемы 3 без артефакта | Синтетика на значениях из интервалов КТРУ: пороги раздела 5 для заглушек и ×1000; тест неизменности проходит |
| 3 | Профилирование СТЕ: заполненность модели и производителя, доли заглушек и повторов, число различных названий свойств, кривая покрытия, запрос на размер | Ответы на открытые вопросы числами | Отчёт с измеренными величинами; уточнена оценка размера артефакта |
| 4 | Слой очистки с флагами и согласование по модели | Чистая основа для статистики | Модульные тесты на четырёх примерах из постановки; отчёт долей флагов по направлениям |
| 5 | Привязка к типам для пилота: по несколько самых крупных типов в каждом направлении | Проверка каскада на малом объёме | Аудит: точность не ниже порога в принятой корзине |
| 6 | Артефакт версии 0: статистика по ключам названий СТЕ, манифест, проверка при запуске, работа без файла | Инфраструктура артефакта | Две сборки дают одинаковый `content_hash`; сервис стартует с файлом, без файла и с чужим снимком КТРУ |
| 7 | Вердикты о свойствах вне КТРУ (2.6) по статистике СТЕ и второму листу | Решена проблема 2 на пилотных типах | Ручной просмотр вердиктов по самым частым свойствам пилотных типов; сообщения согласованы с экспертом |
| 8 | Сопоставление свойств СТЕ и КТРУ для пилота: три запрета и подтверждение частых пар | Статистика по свойствам КТРУ | Аудит пар `auto`: точность не ниже порога; «(дерево)» и «(металл)», «Ширина» и «Ширина упаковки» не объединены |
| 9 | Уровень 2: статусы `typical`, `rare`, `unseen` с числами | Решена проблема 1 на пилотных типах | Доля `unseen` на реальных описаниях не выше порога; тест неизменности проходит |
| 10 | Уровень 3 на статистике СТЕ: `scale` по зонам, `outlier`, `dimensions`, парные ограничения | Проблема 3 закрыта полностью | Синтетика с разбиением по производителям: пороги раздела 5 |
| 11 | Калибровка N1, N2 и остальных порогов на обучающих блоках; итоговый замер | Пороги обоснованы данными | Отчёт оценки; пороги записаны в конфигурацию и входят в `config_hash` |
| 12 | Приоритет показа, бюджет замечаний, телеметрия принятых и отклонённых | Интерфейс не перегружен | На реальных описаниях медиана видимых замечаний на запрос согласована с командой; события пишутся |
| 13 | Расширение на все типы; эмбеддинги как генератор кандидатов, только если покрытие привязки недостаточно | Полный охват | Покрытие и точность привязки по направлениям в отчёте; решение об эмбеддингах принято по числам |

**Точки остановки.** После шагов 2, 7 и 9 результат можно выпускать отдельно: каждый из них закрывает одну из исходных проблем целиком или для пилотных типов.

**Зависимости.** Шаги 1–2 и 3–5 идут параллельно. Шаг 7 не ждёт шага 8: вердикты о свойствах работают на ключах названий СТЕ без сопоставления с КТРУ.

## 7. Чего делать не нужно

Общий признак всех пунктов: они либо размывают границу между уровнями, либо дают пометку, причину которой нельзя показать.

| Чего не делать | Почему |
| --- | --- |
| Привязывать товары СТЕ к конкретной позиции КТРУ | Поддержка дробится, а привязка по значениям делает статистику копией интервалов КТРУ |
| Использовать значения свойств для привязки товара к типу | Порочный круг: статистика значений будет отражать правило отбора, а не товары |
| Спрашивать у LLM, «бывает ли так» или каков типичный диапазон | Ответ недетерминирован, числа не привязаны к данным, и он начинает играть роль эталона |
| Обучать детектор аномалий (isolation forest, автоэнкодер) | Нет разметки для настройки и нет причины, которую можно показать пользователю |
| Описывать распределения смесью или KDE | Неустойчиво на малых выборках; таблица частот и зоны дают то же самое точнее и проще |
| Считать среднее и σ | Заглушки и скошенные распределения делают границы бессмысленными |
| Считать статистику по карточкам, а не по моделям | Популярная модель у десятков поставщиков задаёт «типичность» всего типа |
| Подставлять статистику соседнего типа или всего направления, когда данных мало | «Ширина» по всей мебели не говорит ничего о стуле; честнее молчать |
| Объединять названия свойств по сходству строк или эмбеддингов без запретов | Склеиваются «Ширина» и «Ширина упаковки», «(дерево)» и «(металл)» |
| Удалять шумные строки из исходной базы | Теряются воспроизводимость и возможность пересмотреть правило очистки |
| Исправлять значения автоматически, даже «очевидные» | Прямое ограничение задачи; ошибка исправления хуже пропущенной ошибки ввода |
| Давать уровням 2 и 3 влиять на отбор кандидатов, ранжирование кодов или порядок уточняющих вопросов | Это скрытый обход уровня 1; в первой версии влияния нет ни в каком виде |
| Вводить единый статус, где `atypical` стоит рядом с `invalid` | Клиенты начнут трактовать «нетипично» как «несовместимо» |
| Показывать каждое редкое значение | Редкое не значит ошибочное; поток пометок обесценивает настоящие предупреждения |
| Говорить «такого не бывает» | По выгрузкам можно утверждать только «не встречается у N моделей» |
| Считать второй лист (КПГЗ) эквивалентом КТРУ | Это другой классификатор без связи с кодами КТРУ; он годится только как довод о реальности свойства |
| Обновлять статистику по запросам пользователей | Петля обратной связи: повторённая ошибка ввода становится «типичной» |
| Вычислять эмбеддинги или искать по векторам на запросе | Задержка и недетерминированность без выигрыша: поиск по ключу решает задачу |
| Строить инкрементальную сборку заранее | Данные малы; полная пересборка проще и воспроизводима |
| Подбирать пороги на тех же блоках, где считаются итоговые метрики | Оценка получится завышенной и не переживёт новые данные |

## 8. Допущения и вопросы к команде

Рекомендации опираются на девять допущений; если неверно первое, третье или четвёртое, меняются подзадачи 2.1 и 2.3.

**Допущения:**

1. В строке товара СТЕ нет категории КПГЗ; известна только категория файла.
2. Тип КТРУ можно задать парой «нормализованное наименование + ОКПД2», и семейства позиций выводятся из снимка КТРУ автоматически.
3. Поля «производитель» и «модель» заполнены у большинства карточек настолько, что по ним можно группировать.
4. Одна и та же модель встречается в нескольких карточках разных поставщиков.
5. Извлекатель уже отдаёт для каждого признака либо код свойства КТРУ, либо исходное название, а также единицу и оператор.
6. Текущие 15 мс (p50) измерены без сетевых вызовов, и артефакт лежит на локальном диске сервиса.
7. Число категорий на втором листе позволяет сопоставить их с типами вручную.
8. Обновления КТРУ и выгрузок редкие, и пересборка по событию приемлема.
9. Все пороги в документе, помеченные как стартовые или предлагаемые, — это решения для согласования, а не измеренные величины.
