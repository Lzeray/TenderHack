# Живой поиск: описание → два разбора → критерии → SQLite → результаты

## Пользовательский сценарий

Пользователь вводит описание; выбирать тип перед поиском не нужно. После debounce 200 мс алгоритм
распознаёт предмет и характеристики, запрашивает полную область КТРУ и проверяет позиции.
После паузы 1 с автоматически запускается независимый локальный разбор Qwen. Его результат
сопоставляется со схемой базы и дополняет выдачу. Enter лишь ускоряет модельную ветку.
Изменение текста создаёт новую ревизию; старые результаты не применяются.

Основные блоки ответа:
- распознанная группа и предмет;
- характеристики с исходными и нормализованными значениями, единицами и источником;
- **все совместимые конечные позиции КТРУ** из проверенной области, без top-50 и без шаблонов;
- фактические товары из XLSX с общим количеством и переходом по страницам;
- уведомления о противоречиях и уточнение только действительно недостающих данных.

Правила диапазонов, размерностей и Decimal остаются в существующем `Engine`/`validate`.
Модель не пишет в нормативный каталог, не меняет числа/единицы и не выбирает окончательный код.
Смысловые результаты модели могут уточнять поисковую интерпретацию; конечный `matched` на одних
неподтверждённых модельных свойствах не выдаётся. Быстрый независимо проверенный разбор не ждёт модели.

## Данные

- `data/ktru.sqlite`: нормативные позиции и характеристики КТРУ.
- `data/ste.sqlite`: исходные и разобранные данные обоих листов трёх XLSX.
- `data/ste_search.sqlite`: производный FTS5-индекс наименований и структурированных признаков
  299 986 товаров. Строится отдельно; исходные данные не меняет.

Отдельный список СТЕ нужен для свойств вроде цвета: в КТРУ такая характеристика есть не у всех
позиций, а в выгрузке могут быть фактические значения. Совпадение СТЕ не является подтверждением
связи этого товара с кодом КТРУ. В интерфейсе показаны фактически применённые фильтры.

Для поиска СТЕ поддержаны предмет по словоформам, точное числовое равенство с переводом единиц,
цвет и некоторые категориальные/логические признаки. Числа индексируются как нормализованные
десятичные строки, без float. Диапазоны и неизвестные схемы выгрузок требуют дальнейшего покрытия;
непроверенные признаки не объявляются доказанными. Выгрузки содержат шум и не считаются эталоном.

Названия и цвета берутся из каталогов/выгрузок. Для детерминированного распознавания предмета
используется существующий словарный разбор словоформ по названиям КТРУ; ручные алиасы типов
отключены в этой ветке. Семантический fallback и Qwen обеспечивают дополнительный путь.

## Запуск

```bash
# Однократно после импорта XLSX:
.venv/bin/python -m ktru_assist.catalog.ste_search --src data/ste.sqlite --out data/ste_search.sqlite

# Модели должны быть установлены локально, Ollama запущен:
RECOGNITION_MODE=hybrid SEMANTIC=1 LLM_MODE=always LLM_TIMEOUT_S=20 \
  HF_HUB_DISABLE_PROGRESS_BARS=1 TRANSFORMERS_VERBOSITY=error \
  .venv/bin/python -m ktru_assist.cli serve --host 127.0.0.1 --port 8000
```

В гибридном режиме Qwen использует контекст 4096 и максимум 768 токенов ответа. Извлечение
выполняется без перечня характеристик КТРУ: ранний эксперимент с передачей всего перечня
провоцировал маленькую модель заполнять неупомянутые свойства. Проверка и привязка к каталогу
выполняются **после** извлечения. Невалидные цитаты/числа отклоняются; ошибки не стирают быстрый результат.

## Проверка в браузере

`tools/ui_live_search_check.mjs` использует установленный Chrome через CDP (порт 9333), без npm-пакетов.
Он реально вводит текст, не нажимает выбор типа или Enter, ждёт обновления и проверяет пагинацию.

На реальном снимке и реальных XLSX:
- `молоток` → 11 КТРУ / 1063 СТЕ;
- `молоток слесарный` → 1 КТРУ / 263 СТЕ;
- `молоток слесарный 500 г` → 1 КТРУ / 52 СТЕ; отображается `500 г → 0,5 кг`;
- `стул` → 11 КТРУ;
- `стул на металлическом каркасе` → 4 КТРУ;
- `стул на металлическом каркасе с мягким сиденьем и мягкой спинкой` → 1 КТРУ;
- `стол белый` → 2469 товаров СТЕ с фильтром цвета;
- Qwen вызывается автоматически, переход на следующую страницу СТЕ работает, ошибок JS нет.

В единичном браузерном прогоне обновления занимали примерно 230–970 мс, включая debounce и
отрисовку. Это функциональная проверка, не нагрузочный p95. Поиск СТЕ и длинные запросы ещё
нуждаются в оптимизации. Qwen на коротких проверенных описаниях отвечал за 1–5 с; качество
на независимом ручном наборе не подтверждено, модель пока пропускает некоторые признаки.
