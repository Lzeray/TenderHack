# Разбор описания: ошибки и ввод «ключ: значение»

Постановка пользователя (10.10.2026): «стол деревянный столешница лдсп» — тип стол, материал (каркас) дерево,
столешница ЛДСП. Система задавала два лишних вопроса, а после выбора варианта плашка выбора оставалась.
Предложение: разобранная строка после Enter превращается в скрытую строку «тип; ключ: значение; …», так же —
при добавлении характеристики; в видимой строке ввода исправляется только орфография.

## Журнал

### P1. Часть товара и прилагательное (extractor 2.4)

Было: «стол деревянный столешница лдсп» → «стол деревянный столешница» — неоднозначно (значение «Стол» с частью
«столешница»), «лдсп» — неоднозначно (каркас / столешница). Причины:
- слову типа («стол» → «Вид товара: Стол») приписывалась ближайшая часть товара («столешница» в двух словах);
- «столешница» после этого была занята, и «лдсп» оставалось без части.

Стало: слово типа часть товара не получает; прилагательное-значение относится к части, только если согласуется с ней
по роду, числу и падежу («деревянная столешница» — да; «стол деревянный столешница» — нет, «деревянный» про
стол). Существительные-значения («лдсп») не проверяются. Результат: «Вид товара: Стол», «Тип каркаса: Деревянный»,
«Вид материала столешницы: ЛДСП», вопросов о привязке нет.

### P2. Выбор варианта не снимал неоднозначность (engine 2.10)

Интерфейс отправляет ручную правку «свойство = значение варианта». Правка привязывалась, но признак из текста
оставался `ambiguous`: в момент сравнения у него запись из текста («лдсп»), к написанию КТРУ («ЛДСП») она
приводится позже, а сравнение было с учётом регистра. Теперь — без регистра и с значением варианта; признак
получает статус `overridden`, плашка выбора не показывается.

### P3. «свойство: нет» читалось как отрицание (extractor 2.4)

«наличие мягкого сидения: нет» давало `ne Нет` (то есть «есть»). Отрицание в конструкции «характеристика:
значение» — только если после «не / нет / без» есть само значение («материал: не лдсп»).

Проверка P1–P3: pytest 262; стенд полноты (`reports/exp/kr_p2.json`) — ни один из 626 ответов не изменился;
бенчмарк — те же цифры, `dialog_resolved` synthetic 0,985 → 0,992; наборы ветки — изменений по кейсам нет.

### P4. Скрытая строка «тип; ключ: значение» (`ktru_assist/canonical.py`, интерфейс)

Решения команды: интерфейс пересобирается (`npm ci` разрешён); при правке не в конце строки решения сверяются по
фрагментам текста.

Устройство:
- Видимая строка — только для ввода; по Enter в ней исправляется орфография (раскладка, однозначные опечатки:
  «стулл деревяный» → «стул деревянный»), больше ничего.
- Скрытая строка = тип (главное слово и слова, не занятые характеристиками) + характеристики видимого текста в
  виде «Свойство КТРУ: значение» (пересчитываются при каждом запросе) + решения пользователя. Что нельзя записать
  без потери смысла (габариты, подставленная единица, неоднозначное значение), пишется исходным фрагментом.
- Решения пользователя (ответ на вопрос, выбор варианта, ручная правка, удаление) передаются в поиск точными
  ограничениями и живут, пока их фрагмент есть в видимом тексте целыми словами (ответ на вопрос — всегда). Прежде
  интерфейс сбрасывал их при любом изменении текста. Фрагмент, о котором решение уже есть, в строке не повторяется.
- API: `SearchRequest.canonical` (скрытая строка прошлого ответа) включает режим; в ответе — `canonical`,
  `corrected_text`, `type_text`, `query.search_text`. Без `canonical` поведение прежнее (бенчмарк, старые клиенты).

Чтобы поиск по скрытой строке давал то же, что по тексту, в разборе «ключ: значение» (extractor 2.5, engine 2.11):
- сначала ищется свойство с точно таким названием (без регистра и знаков): «Тип: на раме», «Тип ткани/
  трикотажного полотна: смесовая»; при одинаковых названиях под разными кодами — группа с этим значением;
- значение КТРУ, начинающееся с «Без» («Без рукавов»), — значение, а не отрицание;
- «Российский размер: от 48 до 50» — диапазон и у свойства с числовыми строками;
- слова названия свойства перед «:» (кроме первой части) не определяют тип: «Размер (обхват головы)» не давал тип
  «головка»;
- запятые и «;» в названиях и значениях КТРУ при записи заменяются пробелом.

Стенд `experiments/canonical_roundtrip.py` (626 запросов стенда полноты + 12 проб): совпадение с поиском по тексту —
статус 100 %, привязанные характеристики 100 %, совместимые позиции 99,8 % (637 из 638; расходится «дрель,
количество аккумуляторов в комплекте, шт 1»: голое число пишется фрагментом без «шт»). Первая версия давала
91 % / 97 % / 85 %; причины и исправления — выше. Стенд полноты в режиме скрытой строки (`--canonical`): полнота
0,988, точность 0,976 — как у поиска по тексту.

Регрессия поиска по тексту после правок разбора: бенчмарк — `hit@1` synthetic 0,951 → 0,992 (точное название
свойства), наборы ветки — 25 кейсов synthetic лучше, хуже — 0.

Интерфейс (`frontend/src/useSearch.js`, сборка в `ktru_assist/web`): скрытая строка хранится и отправляется с каждым
запросом; ответы и правки после ответа сервера считаются записанными в неё; подсказка о выдаче кода исправлена.
Сценарий в браузере `tools/ui_canonical_check.mjs` (headless Chrome, протокол отладки): «стол деревянный столешница
лдсп» — без вопросов; выбор варианта для «лдсп» убирает плашку, переживает дописанное «деревянный» и уходит со
стёртым «лдсп»; Enter исправляет орфографию в поле ввода; ошибок JavaScript нет. pytest 268, тесты интерфейса 7.
