# TenderHack: план улучшений детерминированного поиска КТРУ

**Назначение:** рабочий план для агента-разработчика.  
**Дата:** 10 октября 2026 года.  
**Основание:** описание системы и решения пользователя в чате. Репозиторий в рамках подготовки плана не изучался; пути модулей ниже — предлагаемая структура, а не утверждение о существующем коде.

## 1. Принятые решения и границы задачи

### 1.1. Целевой результат

Улучшить существующее ядро: свободное описание одного товара → унифицированные характеристики → проверяемое сужение позиций → конечный код либо конкретное уточнение.

Поддержать три группы: одежда, мебель, инструменты. Внутри групп — сотни видов товаров. Группа и тип товара — разные уровни: «мебель» не заменяет «стул», «шкаф» или «подушка на сиденье».

Система должна различать характеристики частей товара: например, цвет сиденья и цвет каркаса. Модельные предложения должны быть объяснимы через исходные фрагменты и правила каталога.

### 1.2. Ограничения

- Linux, веб-интерфейс; первоначально один пользователь.
- Есть RTX 3070, но архитектуру сейчас не привязывать к этой карте. Не обещать, что конкретная конфигурация модели поместится в её память.
- Общий лимит VRAM на инференс — 40 ГБ; реальные расходы всех работающих моделей измерять совместно.
- Запрещены внешние API проприетарных LLM, платные поисковые API и low-code.
- Только открытые модели с проверенной лицензией.
- Агент-разработчик реализует систему и проверки; команда валидирует предметные правила и независимые эталоны.
- Цель — стремиться к нулю ошибочных автоматических решений. Это цель безопасности результата, а не обещание доказанной нулевой ошибки.

### 1.3. Требования по задержке

**Предел 0,5 секунды относится к черновику A**, а не к расширенному разбору B.

- Основная цель: p95 задержки черновика ≤ 500 мс на объявленном наборе запросов.
- Желаемый диапазон: 100–300 мс.
- Измерение: от последнего изменения текста до применения актуального ответа в интерфейсе, включая debounce, ожидание, сетевой обмен и отрисовку.
- Условия: прогретые модели, один пользователь; отдельно измерять холодный старт.
- Задержку B после Enter измерять и показывать отдельно. Пользователь не задал для неё числовой предел.
- Начальный debounce — 100–150 мс как параметр для настройки, а не гарантированный оптимум.
- Таймаут B задаётся конфигурацией. При его истечении сохраняется честный черновик и предлагается ручное уточнение; окончательный результат не выдумывается.

### 1.4. Архитектурный выбор

Начальный состав:

1. Существующее детерминированное ядро.
2. Исправление пробелов правил и словарей.
3. Один лёгкий энкодер для семантических предложений.
4. Один локальный LLM-провайдер для расширенного разбора по эскалации.
5. Контроллер состояния, интерфейс, журнал решений и измерение качества.

Полный набор отдельных классификаторов и токен-классификаторов пока не внедрять. Свободный агентный цикл не включать в обязательный путь пользователя.

## 2. Что сохранить и что изменить

### 2.1. Сохранить

По описанию уже реализованы и должны быть сохранены:

- импорт КТРУ, разрешение версий, проверка статусов и дат;
- шаблоны, родители, обязательность, ОКЕИ и границы диапазонов;
- Decimal и точное преобразование совместимых единиц;
- нормализация, pymorphy3, защищённое исправление опечаток, алиасы;
- valid / invalid / unknown;
- исключение только по доказанной несовместимости;
- фиксированное ранжирование;
- вопросы по минимальному худшему остатку;
- приоритет ручного ввода;
- сброс старых ответов при изменении описания.

Агент сначала сопоставляет это описание с фактическим кодом. Несовпадения фиксирует, а не маскирует новым слоем моделей.

### 2.2. Изменить в первую очередь

| Проблема | Изменение | Как проверить |
| --- | --- | --- |
| Главного слова недостаточно для типа | Реестр типов, составные названия, альтернативы и подтверждение области | Неоднозначный запрос не получает окончательный код из ошибочно суженной области |
| «Сетевой» не распознаётся как «От сети» | Алиасы значений с контекстом свойства и типа | Однозначная формулировка обрабатывается без LLM |
| Нет разделения частей товара | Канонические ключи «компонент + свойство» и отображение на реальные характеристики | Цвет каркаса не переносится на сиденье |
| «45 метров» формально проходит интервал | Отдельные проверенные правила правдоподобия | Предупреждение не выдаётся за запрет КТРУ |
| Нет метрик | Единая схема событий, ручной набор, benchmark | Есть воспроизводимый отчёт без выдуманных чисел |
| Выход модели может стать жёстким условием | Разделить гипотезы, принятые интерпретации и ручное подтверждение | Неоднозначная гипотеза не исключает окончательно правильный код |
| Неясен источник контекста B | Независимый CatalogContextBuilder | Модель получает только существующие свойства и значения из снимка |

## 3. Модули и зависимости

Названия логические. В существующем репозитории адаптировать их к действующим модулям, сохранив полезные интерфейсы.

| Модуль | Ответственность |
| --- | --- |
| CatalogRepository | Позиции, версии, активность, схемы и полный набор области |
| TypeRegistry | Группы, виды товаров, алиасы, связи с позициями, подтверждение покрытия |
| QueryNormalizer | Преобразования с сохранением исходного текста и карты координат |
| RuleExtractor | Явные числа, единицы, отрицания, диапазоны, свойства и алиасы |
| SemanticProposer | Несколько предложений типов/свойств/значений; возможность отказа |
| CatalogContextBuilder | Контекст B из каталога; идентификаторы, схемы, полнота и ограничения |
| StructuredExtractor | Единственный ограниченный вызов LLM, без самостоятельного выбора кода |
| AssertionResolver | Согласование источников, ручные переопределения, связи частей товара |
| ValidationEngine | Проверка КТРУ, единиц, диапазонов, противоречий и unknown |
| PlausibilityChecker | Отдельные предметные предупреждения и подтверждения |
| SearchOrchestrator | Пути A/B, эскалация, версии, повторы, кэш и завершение |
| ClarificationPolicy | Вопросы по полному оставшемуся множеству |
| DecisionTrace | Источники признаков и причины каждого шага |
| Evaluation | Качество, задержки, расход памяти, сравнение вариантов |
| API / UI | Ввод, черновик, подтверждение, ручные правки, объяснения |

ValidationEngine не зависит от конкретной модели. Замена модели не меняет правила соответствия КТРУ.

**Поток A:** текущая версия запроса → правила → при необходимости семантические предложения → отдельный расчёт черновика → UI.

**Поток B:** Enter → снимок состояния → проверка необходимости эскалации → контекст из КТРУ → один вызов LLM → проверка и согласование → полный пересчёт ядром → результат либо вопрос.

## 4. Контракты данных

### 4.1. QueryState

Минимальные поля:

- session_id;
- revision — увеличивается при изменении текста, ручного поля или ответа на вопрос;
- raw_query;
- submitted_revision — версия последнего Enter;
- manual_assertions;
- confirmed_type;
- catalog_snapshot_id и effective_at — фиксированная дата проверки;
- versions — словари, правила, реестр типов, поиск, модели, промпт и схема ответа.

Дата проверки входит в воспроизводимое состояние: изменения активности позиции не должны незаметно менять результат повторного запуска.

### 4.2. RawAssertion

Хранить признаки списком, а не словарём по имени: повторные или противоречащие условия нельзя перезаписывать.

Пример ниже иллюстративный. Предложенный идентификатор не является реальным кодом характеристики КТРУ.

```json
{
  "assertion_id": "a1",
  "source": "semantic",
  "span": {
    "start": 0,
    "end": 13,
    "quote": "черный каркас"
  },
  "component_raw": "каркас",
  "property_raw": "цвет",
  "raw_value": "черный",
  "raw_unit": null,
  "predicate": {
    "kind": "enum",
    "operator": "eq"
  },
  "intent": "assertion",
  "proposed_property_ref": null,
  "alternatives": [],
  "confidence": null,
  "confirmation": "tentative"
}
```

- Координаты start/end: Unicode code points, end не включается. Фронтенд должен корректно переводить их в свои строковые координаты.
- Исходную цитату проверять сравнением с raw_query.
- Сохранять компонент товара, отрицание, оператор и предполагаемое намерение: факт о товаре / требование / предпочтение / неизвестно.
- Для чисел хранить исходную строку; нормализованное Decimal вычисляет код.
- Интервалы имеют отдельные lower/upper и признаки включённости; допускаются неограниченные границы.
- Уверенность модели — вспомогательный сигнал. Косинусная близость и softmax не считаются вероятностью правильности.
- Нераспознанные значимые фрагменты возвращать отдельным списком.
- Для явно указанной пользователем характеристики нельзя подменять исходное значение разрешённым значением из каталога.

### 4.3. ResolvedAssertion

Добавляет:

- канонический ключ, например frame.color или seat.color;
- реальную привязку к схемам соответствующих позиций;
- нормализованное значение и единицу;
- статус разрешения и причину;
- какие источники поддерживают трактовку;
- необходимость подтверждения.

Канонический ключ — внутренняя семантическая сущность. Он не доказывает одинаковую семантику одноимённых свойств разных позиций. Отображение на КТРУ проверяется отдельно.

Идентификатор характеристики берётся из каталога и учитывает позицию/версию, если глобальная уникальность не подтверждена.

### 4.4. CatalogContext

**Контекст B формируется из XML-снимка КТРУ, а не из того, что «выдали агенты».** A лишь предлагает области, которые нужно рассмотреть.

Контекст содержит:

- снимок и дату;
- возможные типы и основание их выбора;
- реальные ссылки на характеристики;
- название, компонент, обязательность, единицы, допустимые значения и интервалы;
- явный список разрешённых property_ref;
- context_id / schema_hash;
- scope_complete и context_complete;
- перечень непереданных схем и причину ограничения, если контекст обрезан.

Не передавать весь каталог в каждый запрос. Собирать схемы релевантных областей и объединять только проверенно эквивалентные характеристики.

Ограничение контекста модели не должно ограничивать окончательную проверку ядра. Если оно мешает пониманию существенного условия, требуется уточнение.

### 4.5. SearchResponse

Минимальные поля:

- session_id, revision, run_id, stage;
- preliminary;
- исходные, предложенные и принятые признаки;
- кандидаты и реальное total_count отдельно от размера выдачи;
- trace шагов сужения;
- ошибки, предупреждения, неизвестные условия;
- выбранный вопрос;
- scope и признаки полноты;
- code_resolution;
- characteristics_completion;
- существующий основной status;
- versions и timings.

code_resolution и полнота заполнения СТЕ — отдельные результаты. Агент должен документировать текущую семантику matched и сохранить её совместимость; новые поля снимают неоднозначность «код один, но обязательные сведения ещё не заполнены».

## 5. Правила доверия и автоматического завершения

### 5.1. Источники

1. Ручные правки и ответы пользователя имеют приоритет над извлечением из текста.
2. Все ручные значения тоже проверяются по единицам и каталогу.
3. Однозначно разобранные кодом исходные числа, единицы и операторы нельзя молча менять выходом модели.
4. A и B предлагают семантические трактовки; B не имеет безусловного приоритета.
5. Существенные расхождения сохраняются как альтернативы и требуют разрешения.
6. Предложение исправления не равно применённому исправлению.
7. После смены описания сохранить существующую политику сброса ответов и явно показывать сброс. Ответы не переносить на другой тип/схему автоматически.

### 5.2. Полнота области

Разделить:

- detected_type: предложение модели/правил;
- confirmed_scope: область, полнота которой подтверждена;
- scope_complete: возможность проверить все позиции этой области.

Для неоднозначных запросов вроде «сидушка» представить альтернативы и запросить подтверждение типа. Top-K используется для отображения и ранжирования, не для доказательства уникальности.

Даже проверка всех позиций одного типа недостаточна, если сам тип выбран ошибочно или охват TypeRegistry неполон.

### 5.3. Условия выдачи окончательного кода

Сохранить существующие проверки завершения и добавить необходимые защиты:

- результат относится к отправленной актуальной версии;
- позиция активна и допустима как конечная;
- область подтверждена и проверена полностью;
- осталась одна возможная конечная позиция;
- применимые существенные условия проверены;
- нет блокирующих неизвестных условий, неразрешённых трактовок или исправлений;
- шаблон и укрупнённая навигационная запись не выданы вместо конечной позиции;
- необходимые требования текущего процесса заполнения СТЕ учтены отдельно.

Нельзя обосновать окончательный код одним высоким score, согласием A и B или одним результатом ограниченной выдачи.

Неясные модельные предположения можно использовать в черновом пересчёте, но они не должны изменять подтверждённое состояние.

### 5.4. Правдоподобие

- Ввести версионированные правила с областью действия, основанием и серьёзностью.
- Отрицательная физическая величина или неверная размерность проверяются по соответствующим явным правилам.
- «45 метров» для высоты конкретного товара — предупреждение, пока предметное ограничение не подтверждено.
- Не заменять 45 м на 45 см автоматически.
- Не переносить диапазон одной категории на другую.
- Вторичные XLSX и статистические выбросы не являются безусловным источником истинности.
- Подозрительное неподтверждённое значение, влияющее на результат, блокирует автоматическое завершение и требует подтверждения.

## 6. Политика путей A и B

### 6.1. Этап A

На каждую актуальную версию после debounce:

1. Нормализация с сохранением исходного текста и преобразований.
2. Защищённые словари и правила.
3. Поиск и несколько трактовок типа.
4. Семантическое сопоставление только неразобранных или неоднозначных фрагментов.
5. Проверка привязок и построение независимого черновика.
6. Расчёт ядром и показ предварительных результатов.

Справочные эмбеддинги вычислять заранее. Не запускать модели для каждого кандидата отдельно, если достаточно сравнения готовых векторов.

Качественные признаки частей товара сопоставлять отдельно. Например, «красное сиденье, чёрный каркас» не превращается в общий список цветов всего изделия.

### 6.2. Этап B

Вызывать после Enter, когда есть:

- существенные нераспознанные фрагменты;
- неоднозначные типы или свойства;
- слабое/неоднозначное сопоставление;
- конфликт, который может объясняться ошибкой разбора;
- not_found при неподтверждённой трактовке типа;
- неразрешённая связь свойства и части товара.

Не вызывать B только ради переформулирования уже понятной ошибки размерности или заполнения отсутствующего значения.

Порог эскалации задаётся конфигурацией и затем настраивается на ручной валидации. Не использовать произвольное «confidence > 0.8 значит верно».

В тестовом режиме B прогоняется и на запросах, которые A считает завершёнными: это выявляет уверенные скрытые ошибки политики эскалации.

### 6.3. Требования к LLM

- Один вызов на отправленную версию в обычном сценарии.
- JSON по ограниченной схеме; guided decoding не заменяет смысловую проверку.
- property_ref только из переданного списка либо null.
- Исходные значения и единицы сохраняются даже при их недопустимости.
- Возвращаются цитаты, неоднозначности и предложения исправлений.
- Нет выбора кода, преобразования единиц или решений о соответствии.
- Нет исполнительных инструментов: пользовательский текст обрабатывается как данные.
- Синтаксически невалидный, обрезанный или не прошедший проверки ответ не применяется.
- Допустим один ограниченный повтор только при техническом сбое; без бесконечного цикла «попробовать иначе».
- При отказе, таймауте или недоступности провайдера — ручное уточнение, а не догадка.

B получает исходный текст; черновик A помечается как гипотеза. В оценке отдельно сравнить B с черновиком и без него, чтобы обнаружить привязку к ошибкам A.

### 6.4. Согласование

B возвращает новый полный разбор. AssertionResolver сопоставляет его с исходным текстом, ручными данными и предыдущими предложениями.

Не дописывать B к старому списку фильтров. Ядро пересчитывает результат с начала для согласованного набора текущей версии.

При смене принятой трактовки показывать изменение: «Материал каркаса уточнён с … на …». Числа кандидатов могут увеличиваться при изменении запроса; искусственная монотонность не нужна.

## 7. Состояние интерфейса, гонки и кэш

### 7.1. Состояния

- editing / draft: актуальный предварительный разбор;
- submitted / processing: зафиксированный запрос обрабатывается;
- resolved: код или конкретный вопрос;
- stale: отображаемый старый результат помечен как устаревший;
- provider_error: расширенный разбор недоступен, остаётся ручной путь.

Модельные поля показывать как «предложено», подтверждённые — как «подтверждено». Проверку по КТРУ отображать отдельным статусом.

Счётчики черновика пояснять: «При текущей предварительной трактовке осталось N позиций». Если черновой тип не подтверждён, не показывать N как окончательное количество подходящих товаров.

### 7.2. Правила применения ответов

- Ответ применяется только при совпадении session_id и revision.
- Для одной revision окончательный результат/результат B не перезаписывается поздним A.
- Ручное изменение увеличивает revision и делает несовместимые вычисления устаревшими.
- Ввод после Enter начинает новую версию и снимает актуальность старого результата.
- Отмена на клиенте не считается гарантией прекращения инференса; проверка версии обязательна.
- В очереди оставлять актуальные задания; устаревшие по возможности отменять до выполнения.
- Старый ответ можно записать в журнал для диагностики, но нельзя применить к UI.

### 7.3. Ключи кэша

| Слой | Обязательные составляющие ключа |
| --- | --- |
| Каталожные эмбеддинги | Текст и идентификатор записи, ревизия энкодера, pooling, нормализация |
| A | Исходный текст, влияющие ручные поля, снимок, версии словарей/правил/моделей |
| B | Полный фактический вход модели, JSON Schema, context/schema hash, ревизия модели, параметры и версия обработки ответа |
| Ядро | Согласованные признаки, область, снимок, effective_at, версии правил и ранжирования |

Не включать revision в семантический ключ повторно используемого результата; при выдаче из кэша создавать новую служебную оболочку с актуальной revision.

Не кэшировать частичный/невалидный ответ как успешный. Кэш не исправляет ошибки модели и не заменяет проверку качества.

Сохранять versions и trace так, чтобы ядро можно было повторно выполнить без модели по сохранённым структурированным условиям.

## 8. Выбор моделей и настройка

### 8.1. Обязательный первый эксперимент

**SemanticProposer: cointegrated/rubert-tiny2.**

- Русский энкодер, 29,4 млн параметров, MIT.
- Сравнение с короткими описаниями и проверенными примерами типов, свойств и значений.
- Это предложение кандидатов по смыслу, а не готовый товарный токен-классификатор.
- Скорость, память и качество измеряются на целевом наборе.

**StructuredExtractor: Qwen3-4B-Instruct-2507 как первый кандидат.**

- Открытая модель с Apache 2.0 и режимом без thinking.
- Провайдер изолирован интерфейсом; замена на другой допустимый checkpoint не меняет ядро.
- Рантайм выбрать после проверки structured output и ресурсов: например, vLLM или llama.cpp.
- Версии и ревизии закрепить; не использовать «latest» как воспроизводимую конфигурацию.
- Проверить квантизацию отдельно; снижение памяти не доказывает сохранение качества.
- 8B проверять только при обнаруженном и измеримом дефиците 4B.

Наличие интерфейса провайдера и тестовых fixtures не означает готовность реального инференса. Если модель не запускалась, агент указывает это явно.

### 8.2. Отложенные эксперименты

| Причина ошибок | Следующий эксперимент |
| --- | --- |
| Не хватает семантического покрытия | Сравнить rubert-tiny2 с multilingual-e5-small |
| Плохо выделяются фрагменты | Проверить мультиязычный GLiNER либо дообученный токен-классификатор |
| Много ошибок закрытых типов | Проверить обученную голову классификации на том же энкодере |
| Ошибки связи части и свойства | Добавить разметку отношений; одной BIO-разметки может быть недостаточно |
| B часто исправляет ошибки A | После проверки примеров использовать их как обучающие данные |
| B добавляет ошибки | Изменить контекст/промпт либо оставить отказ и ручное уточнение |

Все дополнительные модели вводятся через флаги. После каждого эксперимента измерять отдельный выигрыш и стоимость.

## 9. Данные и оценка качества

### 9.1. Независимый ручной набор

Целевой первоначальный объём — 150–300 случаев, если команда успевает их проверить. При меньшем объёме публиковать фактический размер и ограничение оценки.

Разметка:

- исходный запрос;
- допустимые трактовки типа;
- признаки, исходные фрагменты, компоненты, операторы, значения, единицы;
- допустимые коды либо необходимость уточнения;
- ошибки и предупреждения;
- сведения, без которых автоматический ответ необоснован.

Выделить dev для настройки и закрытый test для проверки. Спорные случаи проверяет второй участник команды.

Агент создаёт схему разметки, средства запуска и отчёт. Предметный эталон не утверждается автоматически той же моделью, которая оценивается.

### 9.2. Синтетика

Использовать КТРУ для генерации случаев с известными свойствами, границами и единицами. Добавлять словоформы, опечатки, перестановки, отрицания, пропуски и конфликты.

- Все варианты одного исходного примера держать в одном разделе.
- Не считать код генерации единственным правильным без проверки остальных позиций.
- Разговорные примеры вроде «сидушка» размечать с альтернативами.
- Включить неизвестные типы, свойства и запросы вне поддерживаемой области.
- Отдельно проверять опечатки в значимых словах и защиту чисел, моделей, единиц.
- Синтетика не является независимой оценкой живых пользовательских запросов.

### 9.3. Метрики

- Точность типа, Recall типов@K, корректность отказа.
- F1 фрагментов и точность отношений «часть — свойство — значение».
- Точность полной характеристики, включая отрицание, оператор и единицу.
- Recall кодов@K и полнота подтверждённой области.
- Доля неправильных автоматических кодов среди автоматических решений.
- Доля unsafe_matched: завершение при нарушенных гарантиях, даже если угаданный код оказался допустим.
- Покрытие автоматизацией и доля manual_choice / уточнений.
- Количество уточнений и правильность завершения диалога.
- Доля эскалаций, исправлений B и новых ошибок B.
- Задержки A/B/ядра и end-to-end p50/p95.
- Пиковая память процесса и VRAM всех провайдеров.
- Таймауты, отказы, устаревшие ответы и воспроизводимость.

Точность автоматических решений всегда показывать вместе с покрытием: отказ на всех запросах не считается успехом.

Цель выпуска: **0 наблюдаемых incorrect_matched и unsafe_matched на согласованном закрытом наборе**. Это не доказательство нулевой ошибки вне набора.

Если среди n автоматических решений нет ошибок, ориентировочная верхняя 95%-граница ошибки по правилу 3/n всё ещё ненулевая. При малом n выводы об уверенности ограничены.

### 9.4. Сравнение конфигураций

1. Усиленное ядро без моделей.
2. Ядро + B для каждого Enter.
3. Ядро + один SemanticProposer + B по эскалации.
4. Дополнительный токен-классификатор — только после сравнения первых трёх.

Настраивать на dev, измерять на одном test. Отдельно показать исходные запросы, на которых появились исправления и регрессии.

## 10. Критические проверки и критерии приёмки

### 10.1. Проверки правильности

- «0,75 кВт» и «750 Вт» дают эквивалентные числовые условия.
- «750 кг» для однозначно указанной мощности вызывает ошибку размерности.
- Вольты не превращаются в ватты.
- Открытые/закрытые границы и пересекающиеся интервалы сохраняются.
- Частичное пересечение диапазонов не выдаётся за полное подтверждение.
- Факт о товаре отличается от требования к будущему товару.
- «Без удара» не превращается в наличие ударного режима.
- Отсутствие свойства у кандидата не считается valid.
- Неизвестное свойство не объявляется несуществующим без основания.
- «Чёрный каркас, красное сиденье» сохраняет отдельные привязки.
- Неоднозначный «сидушка» не получает код только по первой гипотезе.
- Единственный результат top-K не означает единственную позицию.
- Последняя закрывающая версия не приводит к возврату старой активной записи.
- Шаблон не выдаётся конечным кодом.
- «45 метров» не исправляется автоматически в сантиметры.
- Несогласие A и B не скрывается.
- Не применяются выдуманные идентификаторы или несовпадающие цитаты.
- Значение, отсутствующее в перечислении КТРУ, сохраняется для диагностики.
- Пользовательская инструкция внутри описания не даёт модели исполнительных действий.

### 10.2. Проверки состояния

- A для revision 10 приходит после результата revision 11 и игнорируется.
- Поздний A не перезаписывает B той же revision.
- Ручная правка во время B делает ответ B устаревшим.
- Смена описания сбрасывает старые ответы согласно текущей политике.
- Ответ из кэша получает правильную актуальную оболочку.
- Таймаут B оставляет честное состояние и возможность уточнения.
- Перестановка фиксированных условий не меняет итог ядра.
- Добавление строгого условия не увеличивает множество кандидатов при неизменной области и интерпретации.
- После исправления условия выполняется пересчёт с начала.

Для реальных каталожных проверок агент сохраняет небольшие fixtures с происхождением, версией и вручную сверенными ожиданиями. Иллюстративные данные помечаются как fixtures; их результаты не называются точностью на реальном каталоге.

### 10.3. Приёмка этапов

- Изменения ядра не обходят действующие проверки.
- Черновые гипотезы отделены от подтверждённых данных.
- Контекст B соответствует реальному снимку.
- Нет неконтролируемого агентного цикла.
- Есть независимая оценка и раздельные метрики путей.
- Целевые задержки подтверждены замерами либо честно отмечены как недостигнутые.
- При выключенных моделях остаётся рабочее детерминированное решение.
- Новый модуль можно отключить флагом без потери базового сценария.
