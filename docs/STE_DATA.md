# Подготовка и разметка XLSX СТЕ

## Запуск

Из корня `ThenderHack`:

```bash
.venv/bin/python -m ktru_assist.catalog.ste_importer \
  --src "../Примеры выгрузок" \
  --out data/ste.sqlite \
  --report reports/ste_quality.json \
  --review reports/ste_review.csv
```

На Linux/Windows путь к Python можно заменить на `python`. Новых пакетов для чтения Excel не требуется: XLSX читается через ZIP/XML стандартной библиотеки. Исходные файлы не меняются. Импорт строит новую базу через временный файл; после успеха заменяет прежний результат. Если процесс прерван, перед повторным запуском следует удалить только созданный им `data/ste.tmp`.

`data/ktru.sqlite` не изменяется. Из него читаются названия характеристик для вспомогательного словаря. Выходная база СТЕ пока не подключена к поисковому API.

## Оба листа каждого файла

1. `Лист1`: товары СТЕ, шесть основных столбцов. Сохраняются исходные клетки, характеристики, файл, лист, номер строки и ID СТЕ.
2. `Лист2`: типовые характеристики категорий ПП, КПГЗ и связи с эталонными характеристиками СПГЗ. Сохраняются все 11 столбцов. Эти связи не являются кодами КТРУ.

Неизвестная схема заголовков вызывает ошибку вместо молчаливой потери данных. Дополнительные клетки строк товаров сохраняются в `raw_cells` и помечаются `extra_columns`.

## Таблицы

| Таблица | Содержание |
| --- | --- |
| `sources` | Имена XLSX, категории по имени файла, SHA-256 |
| `products` | Строки товаров, исходные клетки, статус качества, поля будущей ручной разметки |
| `features` | Сегменты строки характеристик, разобранные имена/значения, единицы и числа |
| `category_properties` | Строки второго листа, исходные значения, связи и метки качества |
| `issues` | Причины проверки товарных строк и характеристик |
| `meta` | Версия парсера и сводка |

Каждая исходная строка сохраняется; дубликаты не удаляются. Пустые строки учитываются отдельно. Категория по имени XLSX — категория источника, а не подтверждённая классификация товара: например, файл одежды включает рюкзаки.

## Парсинг и автоматические метки

Разбор характеристик: явный разделитель `:` → самый длинный известный префикс названия → числовая граница. Словарь состоит из названий второго листа, КТРУ, небольшой явной базы названий и обнаруженных числовых префиксов. Метод записывается для каждого сегмента. Словарь из числовых префиксов может содержать ошибочные границы; совпадение не является доказательством корректности разбора.

Неразобранный сегмент сохраняется целиком. Категориальные значения не разбиваются автоматически по запятым, чтобы не потерять составные значения. Сохраняются числа, диапазоны и габариты; оси габаритов не угадываются. Decimal используется для сравнения и приведения распознанных единиц к базовой единице размерности из `units.py`. Встроенные в имя единицы не додумываются; неизвестные составные единицы сохраняются для проверки.

Метки:
- `missing_field`, `missing_value` — пустые поля и значения-заглушки;
- `duplicate_ste_id` — повтор ID, исходные строки сохраняются;
- `duplicate_feature` — повтор свойства с эквивалентным значением;
- `conflicting_feature_values` — повтор свойства с различающимися значениями, требующий проверки;
- `unresolved_property` — не удалось отделить имя свойства;
- `unrecognized_unit`, `unit_not_specified` — единица неизвестна или не указана;
- `zero_value_review` — нулевое число, не обязательно ошибка;
- `reversed_range` — у разобранного диапазона начало больше конца;
- `dimension_axes_unassigned` — габариты без подтверждённой привязки осей;
- `extra_columns` — дополнительные клетки.

Второй лист отдельно помечается при отсутствующем имени свойства, отсутствующих допустимых значениях и неизвестной единице.

**Это автоматическая разметка качества, не эталон «СТЕ → КТРУ» и не измерение точности парсера.** `needs_review` может означать допустимое число без единицы или корректные габариты. `parsed` не означает «товар проверен экспертом». Невероятные значения вроде диаметра 1212 мм пока не классифицируются как физически невозможные: нужны правила конкретного семейства товаров.

## Ручная проверка и дальнейшая разметка

`reports/ste_review.csv` — небольшая детерминированная выборка: до 30 примеров каждого типа проблемы для каждого XLSX; также примеры второго листа. Это не случайная выборка для оценки точности. CSV в UTF-8 с BOM для Excel.

Для каждой записи доступны источник, лист, строка, ID записи, проблема, фрагмент и полный контекст. Эксперт заполняет:

- `review_decision`: например, `confirmed`, `false_positive`, `uncertain`;
- `corrected_property`, `corrected_value`: только подтверждённое исправление;
- `verified_ktru_code`: необязательный код после отдельной проверки по действующей конечной позиции КТРУ;
- `reviewer`: автор разметки.

Заполненный CSV следует сохранить отдельным файлом, чтобы повторный импорт его не перезаписал. Автоматического применения ручного CSV в базу пока нет. Следующий этап — проверить выборку, скорректировать правила парсинга и подготовить отдельный, независимо проверенный набор сопоставлений с КТРУ.

## Проверки кода

Новые тесты проверяют преобразование единиц, диапазоны, габариты, сохранение неизвестных фрагментов, повторяющиеся ID, эквивалентные и конфликтующие значения, сохранение исходных строк и импорт второго листа.

На текущем состоянии проекта: 98 pytest-тестов прошли. Старый evaluator поискового движка дал 26/28 ожидаемых статусов и 0/28 повторяемых полных ответов: текущий ответ содержит новые изменяющиеся `timings`, которые evaluator не исключает. Не считать этот прогон подтверждением повторяемости или регрессией XLSX-импорта: модуль подготовки СТЕ не подключён к движку. Кейсы T09 и F05 требуют отдельной проверки актуального движка; результаты сохранены вне репозитория, прежние отчёты не перезаписаны.
