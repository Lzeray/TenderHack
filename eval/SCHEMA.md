# Формат разметки кейсов оценки

Один кейс — одна строка JSONL. Поля прежнего формата (`eval/cases.jsonl`, `eval/holdout.jsonl`) поддерживаются
без изменений. Новые поля необязательные.

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | строка | уникальный идентификатор |
| `split` | `dev` \| `test` | `dev` — для настройки, `test` — закрытый набор, только для итоговой проверки |
| `source` | `manual` \| `synthetic` \| `ste_export` | происхождение текста |
| `group` | строка | исходный пример: все его варианты (опечатки, перестановки) должны быть в одном `split` |
| `category` | `clothes` \| `furniture` \| `tools` \| `out_of_scope` | направление |
| `text` | строка | исходный запрос пользователя |
| `expected_code` | строка \| null | эталонный код (прежний формат) |
| `acceptable_codes` | список | все коды, которые эксперт считает верными; если задан, заменяет `expected_code` |
| `expected_status` | список | допустимые статусы ответа |
| `acceptable_types` | список | допустимые трактовки типа: наименования позиций КТРУ |
| `must_not_auto` | bool | автоматический код здесь недопустим (неоднозначность, вне области, нужно уточнение) |
| `expected_features` | список | признаки: `{quote, component, property, op, value, value_to, unit, negated, intent}` |
| `expected_issues` | список | коды обязательных предупреждений (`implausible_value`, `unknown_property`, …) |
| `must_explain` | строка | подстрока, которая должна быть в ответе |
| `verified` | строка | основание эталона: по каким характеристикам КТРУ проверено |
| `labeled_by`, `reviewed_by` | строка | кто разметил и кто перепроверил (второй участник — для спорных) |

Правила разметки:

- Эталон утверждает команда. Модель, которую оцениваем, эталон не утверждает.
- Код ставится, только если проверены **все** позиции области: если описанию соответствуют несколько позиций,
  в `acceptable_codes` записываются все они, либо `must_not_auto=true` с ожидаемым вопросом.
- Разговорные формулировки («сидушка») размечаются с альтернативами в `acceptable_types`.
- Числа и единицы в `expected_features` записываются так, как в тексте (без перевода).
- Синтетика (`source=synthetic`) — это не независимая оценка живых запросов, её отчёты публикуются отдельно.

Метрики (`eval/run_benchmark.py`):

- `incorrect_matched` — выдан `matched`, а код не входит в допустимые (или код недопустим вовсе).
- `unsafe_matched` — выдан `matched`, а независимая перепроверка гарантий не прошла:
  в полной области типа больше одной совместимой конечной позиции, позиция — шаблон или неактивна,
  есть неподтверждённые гипотезы моделей, область неполная. Считается **даже при угаданном коде**.
- `coverage` — доля автоматических `matched` среди всех кейсов. Точность всегда показывается вместе с покрытием.
- `resolved_dialog` — доля кейсов, дошедших до верного кода в симулированном диалоге (не больше 6 вопросов).
- Задержки A, B и сквозная — p50/p95. Пиковая RSS процесса и VRAM (по `nvidia-smi`).
- Для B: доля эскалаций, исправления (B привёл к верному коду, который черновик не дал) и новые ошибки
  (верный код был совместим в черновике и потерян после B).

Если среди n автоматических решений ошибок нет, ориентировочная верхняя 95%-граница доли ошибок — 3/n
(«правило трёх»). Отчёт печатает её рядом с нулём.
